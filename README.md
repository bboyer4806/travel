# Travel
A shared notebook for travel ideas: trips, ordered destinations, transportation between departing city, destinations, and return city, hotel alternatives, activities, restaurants, and estimated budgets. Each city's research stays in Destinations, shared by every trip that visits it.

## Start locally
Requires Node 24 and pnpm 10.32.1.
```sh
pnpm install --frozen-lockfile
pnpm dev
```
Open http://localhost:3000 and sign in with Google. The server refuses to start, in `pnpm dev` and in production, until these server-only settings are in `.env.local` (excluded from Git); see [Google Sign In](#google-sign-in):

```sh
# From a Google OAuth web client whose redirect URIs include http://localhost:3000/auth/google/callback
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
# The Google account authorized to use Travel
TRAVEL_OWNER_EMAIL=
```

There is no stand-in for Google, so signing in locally needs that real client.

Local data is stored in `data/travel.sqlite`. It is excluded from Git. Set `TRAVEL_DATABASE_PATH` to choose another location.

## Google Sign In
Sign in with Google is the only way in, and Travel signs in the same way as Budget and Meals: the OpenID Connect code flow with PKCE, written by hand in `src/lib/google.ts`, with sessions kept in Travel's own database. Every page, saved change, photo, image added by URL, city suggestion, feedback message and What's new entry requires signing in. Only the sign-in page (`/login`), the Google routes under `/auth/google`, and `/api/health` are public, apart from what ChatGPT and Claude need to connect: OAuth metadata under `/.well-known`, and the registration and token endpoints under `/api/oauth`. The MCP endpoint, `/api/mcp`, takes only an AI connection's access token, never a session (see [AI assistants](#ai-assistants)).

- **Who can sign in.** The Google account named by `TRAVEL_OWNER_EMAIL` is authorized when the app starts; access never depends on who signs in first, and nobody can register themselves. An email is also authorized when a trip owner shares a trip with it (TRA-104), even before that person has ever signed in. Authorization is permanent, even if every shared trip is later revoked. Authorized people can create their own trips.
- **Identity.** Travel uses only what Google's ID token says. The email must be verified by Google, and the first sign-in binds the authorization to Google's stable account identifier, so a reassigned email address cannot take over the account, and an account keeps access if its email changes. Google passwords and OAuth tokens are never stored.
- **Sessions.** Signing in starts a session that lasts 30 days from last use, across navigation and refreshes. The browser holds a random token in an HttpOnly, SameSite=Lax cookie, Secure and `__Host-` prefixed over HTTPS, and the database keeps only a hash of it. Every request checks the session against the database; an expired, unknown or altered token is refused. **Sign out** in the header ends the session on the server and removes the cookie.
- **Turned away.** Signed-out visitors go to the sign-in page, and after signing in start from All trips. The sign-in page says why when Google sign-in is refused:

| Google came back with | The sign-in page says |
| --- | --- |
| An account that hasn't been given access | This Google account doesn't have access to Travel, with a reminder to choose another account or ask a trip owner to share a trip |
| An email Google hasn't verified | Google hasn't verified this account's email address |
| A sign-in that didn't start in this browser, or started over ten minutes ago | That sign-in expired |
| A failure exchanging Google's code | Google sign in didn't finish |
| Cancel, on Google's screen | Nothing |

None of these creates a session. A save attempted after the session ends keeps the editor open and asks you to sign in again in another tab. Saved photos are served with private caching, so shared caches never store them.

## Sharing trips
Each trip has one owner and is private to its owner until shared (TRA-104).

- **Owners.** A new trip belongs to the account that creates it. Trips from before sharing belong to the designated owner, `TRAVEL_OWNER_EMAIL`, assigned once by the schema 20 upgrade and never by who signs in first. Ownership can't be transferred.
- **Sharing.** On the trip's page, the owner chooses **Share** and enters a Google account's email address, including someone who has never signed in to Travel. That email becomes authorized to sign in, and the trip appears in their list once they sign in with that Google account. Travel sends no invitation, email or link, so tell them yourself. An email can be added to a trip once; adding it again, or the owner's own email, is refused.
- **What shared people can do.** Everything in the trip: its details and dates, tagline, focus, headline image, tags, destinations, travel, hotels, activities, restaurants, churches, entry requirements, health and safety, budgets, At home items, packing list and photos, and each likes the trip and what is in it for themselves (see [Likes](#likes)). The destinations it visits are the owner's, shared by the owner's other trips that visit them, so a change to one appears in those trips too (see [Destinations](#destinations)). Only the owner can delete the trip, share it, or remove someone, and the Share and Delete controls appear only for the owner. There are no view-only or custom roles.
- **Who has access.** The Share dialog lists the owner and everyone the trip is shared with, each with **Remove**. Trip lists show both your own trips and trips shared with you, marked **Shared by** their owner. **Access** in the header shows who can open every trip and destination you can (see [Access](#access)).
- **Removing access.** Takes effect on that person's next request: the trip leaves their list, its pages and saved links show "This page has moved on.", saves are refused and photos, the trip's headline image included, are no longer served. Its destinations leave their Destinations too, unless another trip shared with them visits them. Nothing in the trip changes. Their email stays authorized, so they keep their own trips and any others shared with them. Photos their browser already downloaded can stay in that browser's cache.
- **Working together.** Everyone with access works on the same saved trip, and changes appear when the page reloads, including after each save. There are no live updates or edit conflict checks: the last save wins.
- **Enforcement.** The server checks the signed-in account against the trip or destination on every page, Server Action and photo request, finding each item's trip or destination from what is saved rather than from what the browser sends. A trip or destination you can't open looks the same as one that doesn't exist.

## Access
**Access** in the header, after Destinations, shows who can open each trip and destination you can, in two tables, Trips and Destinations, without opening each one (TRA-162).

- **Trips.** Every trip you can open, your own and those shared with you, with its **Owner** and **Who has access**: its owner, then everyone it is shared with.
- **Destinations.** Every destination you can open, as Destinations lists them, in a trip or not, each once however many trips visit it, with its owner and who has access. A destination is open to its owner and to everyone a trip that visits it is shared with, as everywhere else in Travel; destinations have no sharing of their own.
- **People.** Each person shows by their Google name and email, or by email alone until they first sign in, as in the Share dialog.
- **What you see.** Everyone with access to your own trips and destinations. For one shared with you, its owner and you, with "Only its owner sees who else has access.", since only an owner sees who else a trip is shared with. The page is built on the server from your own access, so nothing more about anyone's sharing reaches your browser.
- **Searching and sorting.** Each table has its own search, which finds trips by name and destinations by city, ignoring letter case. Both tables are in alphabetical order; select **Trip** or **Destination** at the top of the first column to sort Z to A, and again for A to Z. Select a trip or destination to open its page.
- **Read-only.** Nothing on the page changes who has access: a trip's owner shares it, or removes someone, with **Share** on the trip's page. Access shows sharing as it was when the page loaded, so refresh it to see changes, including access that has ended.
- **Phones.** A table too wide for the screen scrolls sideways within its own box, and the page never does. With Access, the designated owner's header has six links, which stay on one line down to 390 pixels wide and wrap within the screen below that; everyone else's five stay on one line down to 320 pixels.

## Likes
Everyone who can open a trip, destination, hotel, activity, restaurant or church can like it, to show the others what interests them without changing the plan (TRA-31).

- **Liking.** Select an item's heart to like it, and select it again to remove your like, at once, with no Save. Each person likes an item once at most. The heart is filled while you like the item and outlined while you don't, and the number beside it is how many people like it, 0 included. As with other changes made without an editor, it shows what is saved: it changes once the save succeeds and the page reloads, keeps keyboard focus, and a save that fails leaves it as it was, with the error at the bottom of the screen, or in an idea's or church's details, above their buttons. Screen readers hear what it likes and its count, such as "Like Lisbon, 3 likes", and whether it is pressed. On touchscreens it is at least 44 pixels.
- **Where.** A trip's heart is on its card in All trips, after **Edit**, and at the top of its page, before **Edit trip**. A destination's is below its stay's notes on each trip's page, on its card in Destinations, and at the top of its page there, before **Edit destination**. A hotel's, activity's or restaurant's is at the bottom right of its photo in its destination's carousels, beside the pencil on its Hotels, Activities or Restaurants page, and at the top of its details. A church's is at the bottom right of its photo in its destination's **Churches** carousel, beside the pencil on its card on its Church page, and at the top of its details. Liking from the details keeps them open.
- **Shared.** Everyone who can open an item sees the same count, and only their own like as theirs, so one person's like never changes another's. A destination's, hotel's, activity's, restaurant's and church's likes are the same in every trip that visits the destination and on its pages in Destinations, and a trip's are that trip's alone. Travel shows how many people like an item, not who.
- **Only preferences.** Liking never changes **Included**, **Must do**, the chosen hotel, budgets, order, dates or anything else, and nothing chooses, ranks or decides by likes.
- **Kept and removed.** Likes stay through refreshing, signing out and reopening Travel. Removing a destination from a trip keeps its likes, and so does ending someone's access to a trip: their likes stay counted, though they can no longer change them. Deleting a trip, destination, idea or church deletes its likes. They are in the same backups.
- **Who.** Only someone signed in who can open an item likes it, as with every change: the server finds the item's trip or destination from what is saved and refuses anyone else. ChatGPT and Claude can't like anything, as each person likes items themselves; a deletion they propose lists the likes it removes.
- **Not included.** Dislikes, other reactions or ratings, polls, voting deadlines, winners, notifications, comments, a history of likes, a page of what you liked, and likes for travel, budgets, photos, packing items or anything else.
- **Upgrade.** Schema 49 adds them, and nothing starts liked (see [deployment](docs/DEPLOYMENT.md#schema-49-likes-tra-31)).

## Trip tags
Tags such as `Europe`, `Beach` or `Family vacation` group trips without changing their names (TRA-17).

- **Adding and removing.** A trip's page shows its tags under its details, each with a remove button, beside an **Add a tag** field. Type a new tag, or choose one the field suggests from the tags on every trip you can open, then press Enter or **Add**. Removing a tag takes it off that trip only. Tags aren't part of **Edit trip**.
- **One tag, one spelling.** A tag is up to 40 characters, with extra spaces removed. Names that differ only in letter case or spacing are the same tag: a trip has each tag once, and a tag you add takes the spelling it already has on a trip you can open, so `europe` becomes `Europe`. A tag exists while a trip has it. There is no list for renaming or deleting tags across trips, and tags have no colors or icons.
- **Sharing.** Tags follow the trip's sharing: everyone with access to a trip sees its tags and can add and remove them, and changes appear when the page reloads, as for every other change. Suggestions and filters offer only tags on trips you can open, so a tag only on trips you can't open is never shown to you.
- **Trip list.** Each trip card shows its tags. **Filter by tag** above the cards lists every tag on your trips. Select any number of them to show only trips with every selected tag. Tag filters combine with the search and with the months under [Best time to go](#best-time-to-go), so a trip shows only when it matches each. Select a tag again to remove that filter, or choose **Clear tag filters** to remove them all and keep the search. Filters reset when you leave the page, as the search does. The search field is outlined while it has focus, and a card reached with Tab shows a focus ring just inside its edge; the search and cards in Destinations do the same (TRA-87).
- **Deleting.** Deleting a trip deletes its tags, never another trip's. Schema 23 adds tags; existing trips start without any (see [deployment](docs/DEPLOYMENT.md#schema-23-trip-tags-tra-17)).

## Trip order
All trips shows your trips in an order you choose, by dragging them into place (TRA-16), until you choose another order under [Sort by](#sorting-trips) for a while (TRA-177). Travel doesn't sort trips by name, date or last change.

- **Dragging.** Each trip card has a handle, a column of dots beside **Edit**. Drag it with a mouse, finger or pen and let go over another trip's card: the trip takes that card's place, before it when coming from later in the list and after it when coming from earlier. While you drag, the trip's card is dashed and a bar on the card under the pointer shows the side it goes. Dragging near the top or bottom of the window scrolls the page. On touchscreens the handle is 44 pixels square, and a finger on it drags rather than scrolls. Only the handle drags, so selecting a card opens its trip, and **Edit** and delete work as before.
- **From the keyboard.** Tab to a trip's handle, named **Reorder** and the trip's name, and press Space or Enter to pick the trip up. The arrow keys move its place one step at a time, Home and End to the first or last place, showing the same bar, and Space or Enter drops it there. Escape, or moving focus away, puts it back. Screen readers hear each step with the trip's position, such as position 3 of 7, and focus stays on the trip's handle in its new place.
- **Saving.** The new order shows as soon as you let go and saves at once, with **Trip order saved.**; there is no Save button. If saving fails, as when a trip was created or shared with you in another tab since the page opened, the trips go back to their previous order and the error appears at the bottom of the screen. Letting go where the trip started saves nothing. The order stays after refreshing, leaving the page and signing in again.
- **Search and filters.** While a search, tag filter or [month filter](#best-time-to-go) is on, matching trips keep their order, or the one Sort by chooses, the handles are unavailable, and the list says to clear the search and filters to drag trips.
- **Your own order.** Each person's order is their own: moving a trip changes nobody else's list, including everyone it is shared with, and changes nothing in the trip. New trips and trips newly shared with you go at the end, in the order you got them, and the others keep their places. A trip shared with you again after your access ended goes at the end too. Deleting a trip takes it out of everyone's order.
- **Upgrade.** Schema 33 records each person's current order, newest trip first, so no list changes until someone moves a trip (see [deployment](docs/DEPLOYMENT.md#schema-33-trip-order-tra-16)).

## Sorting trips
**Sort by**, below **Filter by tag** and **Best time to go** and above the trip cards on All trips, shows your trips in another order for as long as the page is open, without changing your own order (TRA-177).

- **Sorts.** **Custom order**, your own order, is chosen each time All trips opens. The others are **Most destinations** and **Fewest destinations**, **Most countries** and **Fewest countries**, **Highest estimated cost** and **Lowest estimated cost**, **Budget completeness**, which puts fully estimated trips first, then partially estimated, then not estimated, as their cards say, and **Longest trip** and **Shortest trip**. Choosing one rearranges the cards at once, without reloading the page.
- **What each counts.** Destinations are the stops on the trip's route, as its page numbers them. Countries are the different countries the trip's destinations are in, each counted once. Only a city chosen from a city suggestion says its country, by the country its label ends with; a city typed any other way is never read for one, and a country Travel doesn't recognize isn't counted. Estimated cost is the total on the trip's card, a partial estimate's included, and Travel never converts or adds up different currencies. Length is calendar days from the trip's start date to its end date, both included.
- **Unknown last.** A trip whose value Travel doesn't know comes after the others in either direction, and is never counted as zero: a trip with destinations but no country Travel can tell, a trip with no amount estimated yet, and a trip without a start date or without nights for every stay, which leave its end date unknown. A trip without destinations has none, and no countries. Trips with the same value, or none, keep your own order.
- **With search and filters.** A sort orders the trips that match the search, every selected tag and any selected month (TRA-178).
- **Dragging.** Trips move only in **Custom order** while every trip shows. While another sort is chosen, the handles are unavailable and the list says to choose **Custom order**, and to clear the search and filters while any is on, to drag trips. Choosing **Custom order** shows your own order again.
- **Nothing saved.** Sorting changes no trip, destination, estimate or order, yours or anyone else's. It lasts until you leave the page, as the search and tag filters do. Saved changes to destinations, estimates and dates show in the sorted order as soon as the page shows them.

## Trip headline images
Each trip can have one headline image of its own, apart from its destinations' photos, which gives the trip its look wherever Travel shows it (TRA-133).

- **Adding.** In **Edit trip**, or while creating a trip, **Add image** under **Headline image** chooses a JPEG, PNG, WebP, AVIF, GIF, TIFF, BMP or HEIC image of up to 5 MB from your device (TRA-179), and **Add image by URL** downloads one from its web address, showing it before you use it (TRA-139). Either is checked and prepared as every upload is (see [Images](#images)). Travel never chooses one itself, and there are no image searches or choices from destination photos.
- **Where it shows.** Across the top of the trip's card on All trips, edge to edge above the trip's details, in a 2:1 frame, and as a 3:1 banner on the trip's page, between **All trips** and the trip's name. Each frame has the same shape on every screen. A trip without a headline image looks as it always has, with no empty frame. The trip's name follows the image, so screen readers skip it. Idea pages, Destinations and every other page show no headline images.
- **Cropping.** Under the image, the editor shows how the **Trip card** and the **Trip page banner** crop it, each in its frame's shape, and each crop is separate. Drag the image in either preview with a mouse or a finger to choose what it shows; it moves only as far as its edges, so it always fills the frame. Its **Zoom** slider, from 100% to 300%, zooms in about the point the image is centered on, and works from the keyboard too. Each preview shows its crop as you drag and zoom. A new image starts centered at 100% in both frames. Cropping changes only how the image is shown, never the image itself.
- **Replacing and removing.** **Replace image**, or **Replace image by URL**, chooses another image, which starts uncropped. **Remove image** takes the image off; once saved, the card and the trip's page look as they did without one. For a saved image, **Undo image changes** brings back the saved image and its crops.
- **Saving.** **Save changes**, or **Create trip**, saves the image and both crops with the trip's other details, all together or not at all, and **Cancel** discards every image change. A file whose type and name both say it isn't one of those formats, an empty file, or one over 5 MB is refused as soon as it is chosen, keeping the image already there. A file the server can't read as an image, or a save that fails, shows its error in the editor, which keeps your changes, and the saved image and crops stay as they were. New crops are refused when someone else has replaced or removed the image since the editor opened; refresh and crop it again. The image and its crops stay after refreshing and signing in again.
- **Sharing.** Everyone a trip is shared with sees its headline image and can change it, as everything else in the trip. The image, and its [large version](#large-photo-versions) for the banner on high-resolution screens, are served only to accounts that can open the trip, versioned and with private caching, as photos are. Deleting a trip deletes its headline image. ChatGPT and Claude can propose adding, replacing or removing it, for the owner to approve (see [AI assistants](#ai-assistants)), and a proposal that deletes a trip lists its image among what it deletes.
- **Upgrade.** Schema 34 adds the table for headline images, and every existing trip starts without one (see [deployment](docs/DEPLOYMENT.md#schema-34-trip-headline-images-tra-133)).

## Trip taglines
A trip's page shows its tagline in capitals above its name, in place of AN ADVENTURE IN THE MAKING (TRA-134), and the trip's card on All trips shows it below its name (TRA-167).

- **Entering.** Type it in **Tagline**, below **Trip name** in **Edit trip** or while creating a trip, from the trip's page or its card on All trips: one line of up to 120 characters. It's saved as typed, shown in capitals in the heading's style, and wraps onto more lines on narrow screens.
- **Default.** A trip without one shows AN ADVENTURE IN THE MAKING on its page, and clearing the field and saving shows it again.
- **Saving.** **Save changes**, or **Create trip**, saves the tagline with the trip's other details, and **Cancel** discards it. A save that fails keeps the saved tagline, and the editor keeps what you typed. Saving any other change to the trip keeps it, and it stays after refreshing and reopening the trip.
- **Where it shows.** At the top of the trip's page, and on the trip's card on All trips, directly below the trip's name and above any [Focus](#trip-focus) line (TRA-167). On the card it's shown as typed rather than in capitals, at 14 pixels in the orange accent, so the serif name still leads. It's always shown in full, wrapping onto more lines rather than being cut short, on desktop and phones. A trip without one shows nothing in its place, neither the default nor an empty line, so its card looks as it always has. A changed tagline shows on the card the next time All trips loads. Destination taglines are unchanged.
- **Sharing.** Everyone a trip is shared with sees its tagline and can change it, as everything else in the trip. ChatGPT and Claude can propose a tagline with a trip's other details, and the proposal's page shows it.
- **Upgrade.** Schema 35 starts every existing trip without one (see [deployment](docs/DEPLOYMENT.md#schema-35-trip-taglines-tra-134)).

## Trip focus
A trip's card on All trips can say what the trip is mostly about on a **Focus:** line below its name and any tagline, such as **Focus:** History, architecture, local cuisine (TRA-168).

- **Entering.** Type it in **Focus**, below **Tagline** in **Edit trip** or while creating a trip, from the trip's page or its card on All trips: one line of up to 120 characters, written however you like, such as several interests separated by commas. It's saved as typed, without spaces at either end.
- **Where it shows.** Only on the trip's card on All trips, directly below its [tagline](#trip-taglines), or directly below the trip's name when it has no tagline, after a semibold **Focus:** label, in the card's gray secondary text at 13 pixels, so the name stays most prominent. A long focus wraps onto more lines, even one long word, and is never cut short, on desktop, tablets and phones. A trip without one shows no Focus line, label or empty space, so its card looks as it did, and on wide screens the cities and details of a card with a focus sit lower than those of the cards beside it. The trip's page and every other page don't show it.
- **Saving.** **Save changes**, or **Create trip**, saves it with the trip's other details, and **Cancel** discards it. Clearing the field and saving takes the line off the card. A save that fails keeps the saved focus, and the editor keeps what you typed. Saving any other change to the trip keeps it, and it stays after refreshing and reopening All trips.
- **Separate from the tagline.** The focus and the [tagline](#trip-taglines) are different fields: changing either leaves the other as it was.
- **Sharing.** Everyone a trip is shared with sees its focus and can change it, as everything else in the trip. ChatGPT and Claude read it with a trip's other details and can propose one, which the proposal's page shows as **Focus**. Travel never writes or suggests one itself.
- **Not included.** Searching, sorting or filtering trips by focus, set categories or tags, and a focus for destinations.
- **Upgrade.** Schema 42 starts every existing trip without one (see [deployment](docs/DEPLOYMENT.md#schema-42-trip-focus-tra-168)).

## Best time to go
Each trip's page has a **Best time to go** section, below the [Calendar](#trip-calendar) and above **At home**, for the calendar months that suit the whole trip, considering every destination on it, apart from each destination's [typical weather](#typical-weather) (TRA-178). All trips can then show the trips recommended for the months you choose.

- **Months.** **Add best time to go**, or **Choose the best months** in the section's empty state, opens its editor, with a checkbox for each month from January to December: choose any of them, all 12, or none. The section lists the chosen months as **Recommended months**, in calendar order whatever order they were chosen in.
- **Why, and when not to go.** **Why these months** says why they're recommended, such as their weather, activities, festivals and crowds, and **Times to avoid** describes the times of year that suit the trip less, and why. Both are optional, up to 4,000 characters each, saved as typed without spaces at either end, and shown with their line breaks only when filled in. A trip with notes but no months says **No months chosen yet**.
- **Empty state.** A trip without any shows **When is the best time to go?**, what the section is for, and **Choose the best months**.
- **Saving.** **Save changes** saves the months and both notes together, replacing what was saved, and **Edit best time to go** opens the editor with them. Unchecking every month and clearing both notes removes it, and the empty state shows again. **Cancel** discards the changes. A save that fails shows its error in the editor, which keeps your changes, and the section keeps showing what is saved, with nothing saying it saved. It stays after refreshing, signing out and reopening the trip.
- **Only information.** Saving it never changes the trip's start date, nights, destinations or their order, travel, budget or anything else, and nothing else changes it. Travel never chooses months or writes notes itself.
- **Sharing.** Everyone the trip is shared with sees the same months and notes and can change them, as everything else in the trip, and nobody else can. ChatGPT and Claude read it with a trip's other details and can propose a whole replacement with `trip.bestTime`, which changes nothing else of the trip, for the owner to approve. The proposal's page shows it as **Recommended months**, **Why these months** and **Times to avoid**.
- **Filtering All trips.** **Best time to go**, below **Filter by tag** and above **Sort by**, lists the 12 months by their first three letters, named in full for screen readers. Select any number of them to show only trips recommended for at least one; a trip without recommended months doesn't show while any month is selected. With none selected, it filters nothing. It combines with the search and tag filters: a trip shows only when it matches the search, has every selected tag and is recommended for a selected month. Select a month again to remove it, or choose **Clear month filters** to remove them all and keep the search and tags. The cards change at once, without reloading the page. Selecting a month never moves the others; on phones the months fill the width below their label, four to a row, each at least 44 pixels tall.
- **Nothing saved.** Month filters change no trip and no one's [trip order](#trip-order), and reset when you leave the page, as the search and tag filters do. While any month is selected, trips can't be dragged, as while searching.
- **Not included.** Months Travel works out from weather, forecasts or other data; ranking months; seasons; filtering by times to avoid; showing the best time to go on trip cards; filtering destinations; month filters saved between visits; and changes to destinations' typical weather or monthly averages.
- **Upgrade.** Schema 50 starts every existing trip without one (see [deployment](docs/DEPLOYMENT.md#schema-50-best-time-to-go-tra-178)).

## Destinations
**Destinations** in the header lists every destination you own and every destination a trip shared with you visits, including destinations no longer in any trip (TRA-105). Search by city or trip name. A [map](#map-of-all-destinations) above the cards shows the destinations the search shows. Each card shows the destination's primary photo when it has photos, the city, the trips that visit it, and how many hotels, activities and restaurants are saved for it. When two cities would show the same short name, such as `Newport, Wales, United Kingdom` and `Newport, England, United Kingdom`, their cards also show their full saved names. A destination's page has its photos, [map](#destination-map), notes, budget, [Hotels, Activities and Restaurants](#hotels-activities-and-restaurants), entry requirements, health and safety, typical weather and Church, its Hotels, Activities, Restaurants and Church pages, **Edit destination**, and **In your trips**, which lists each of your trips that visits it.

- **Card photos.** A destination with photos shows its primary photo across the top of its card, edge to edge above its details, in the same 2:1 frame as trip cards' [headline images](#trip-headline-images), on every screen (TRA-131). It fills the frame without stretching, cropped around the focal point saved for it (see [Images](#images)), and selecting it opens the destination, as the rest of the card does. A destination without photos has no photo, frame or placeholder, so its card looks as it always has. Choosing another primary photo, adjusting its crop, or removing it shows on the card the next time the list loads. The city's name follows the photo, so screen readers skip it. Photos are changed only in the destination's editor.
- **New destination.** **New destination** saves a city to research before it is in any trip (TRA-106). Only the city is needed, chosen with the same city search as everywhere else. The destination's page opens next, where you add and edit its photos, notes, budget amounts, hotels, activities, restaurants, churches and research as for any destination. Choosing a city you already have a destination for, in a trip or not, opens that destination instead and saves nothing new. A destination you create is yours, even when a trip shared with you visits another account's destination for the same city.
- **Adding to a trip.** **Add destination** on a trip's page asks only for the city, chosen with the same city search (TRA-107). When the trip's owner already has a destination for that city, such as one created with **New destination**, one researched for another trip, or one removed from this trip, the trip visits it with everything saved for it, copying nothing. Any other city becomes a new destination. Either way it joins the route as the last stop, without nights or stay notes; enter them with its edit control when you know them. Connections between the earlier stops are kept, and the one from the previous last stop to the return city is replaced by connections to and from the new stop. Choosing a city the trip already visits adds nothing: the page shows that stop's card and says the city is already in the trip. A trip that the schema 21 upgrade left visiting a city twice shows its first stay there.
- **Adding between destinations.** A **+** above each destination card on a trip's page, and one below the last card, adds a destination there (TRA-153). Each opens the same **Add destination**, with the same city search and **In your library**, titled with the destination the new one goes before, such as **Add a destination before Florence**; the + below the last card opens it as the heading's **Add destination** does. The city or saved destination chosen joins the route directly before that card, or last, without nights or stay notes. The other destinations keep their order, nights, stay notes and everything saved for them, and the trip keeps its start date. Only the connection where the new stop goes is replaced, by connections to and from it: above the first card, the one from the departing city, and between two cards, the one between them, with what was planned for it. Every other connection keeps its plans. Dates are worked out in route order as before, so the new stay's dates, and those of the stays after it, follow once its nights are entered (see [Trip dates and nights](#trip-dates-and-nights)). **Cancel** adds nothing. A city the trip already visits isn't added again or moved: the page shows its card where it is. With a mouse, the + above and below a card show while the pointer is over the card or a +, or a + has keyboard focus. On touchscreens they always show, 44 by 44 pixels, in the space between the cards. They never cover a card's photos or details. Anyone who can open the trip can use them, as they can Add destination. If the card's destination has left the trip since the page opened, saving says the route has changed and asks you to refresh.
- **In your library.** Add destination's city search also lists saved destinations, first and marked **In your library**, so a city researched in Destinations or for another trip is found however its name was written (TRA-142). One is listed when its name, the text before its first comma, begins with the name you type, ignoring letter case, accents and punctuation, so `Reykjavik` finds `Reykjavík, Iceland`. It also takes the place of any city suggestion that is it: one with its name in every region and country its saved city gives after the name, written out, as a two-letter country code or as a US state's abbreviation. So `Nuuk, GL` and `Nuuk, Greenland` are the suggestion Nuuk, Sermersooq, Greenland, while `Newport, Wales, United Kingdom` isn't Newport, England. A city saved without a region or country, such as `Paris`, could be any Paris, so it is listed beside the suggestions. Each saved destination shows once, named as it is everywhere else, and choosing one adds that destination by its ID, with everything saved for it, unchanged; only its nights and stay notes are this trip's own. A saved destination already in the trip shows its card instead. The list offers the trip owner's destinations that you can open: all of yours on your own trips, and on a trip shared with you, its owner's destinations that a trip shared with you visits, never your own, since a trip visits only its owner's destinations. A city typed in and saved without choosing one works as before. Destinations already saved twice under different names, such as `Nuuk, Greenland` and `Nuuk, Sermersooq, GL`, stay as they are, and both are listed.
- **One destination per city.** Each owner has one destination for each city, shared by every trip of theirs that visits it. Cities match on their full saved name, ignoring letter case, extra spaces, and how accented letters are encoded, so same-named cities in different states, regions or countries stay separate. Adding a city to a trip visits the trip owner's destination for it when there is one, as described above, and renaming a destination to another saved destination's city is refused.
- **Tagline.** A destination's page shows its tagline in capitals above its name, in place of A PLACE WORTH KNOWING (TRA-125). Type it in **Tagline**, below City or destination in the destination's editor, from its page or from any trip's page: one line of up to 120 characters. It's saved as typed, shown in capitals in the heading's style, and wraps onto more lines on narrow screens. A destination without one shows A PLACE WORTH KNOWING, and clearing the field and saving shows it again. On a trip's page, each destination's card shows its tagline whole and as typed, directly below its name and above the stay's notes, in the orange accent, so it stands apart from the name and notes in dark ink (TRA-166). It wraps onto more lines as the notes do, on desktop and phones, and a saved change shows as soon as the save finishes. A destination without one shows nothing there, so its card looks as before. Saving any other detail, from this editor or another, keeps the tagline. Schema 31 starts every existing destination without one (see [deployment](docs/DEPLOYMENT.md#schema-31-destination-taglines-tra-125)). ChatGPT and Claude can propose a tagline with a destination's other details, and the proposal's page shows it.
- **Shared by its trips.** A destination's tagline, notes, photos, hotels, activities and restaurants with their selections (the chosen hotel, included ideas and Must do) and restaurant types, churches and Church visibility, entry requirements, health and safety, typical weather, and every budget amount, rate and method belong to the destination. Change them from its page in Destinations or from any trip's page, and the change appears in every trip that visits it. Renaming its city clears its travel connections in every trip that visits it.
- **Kept by each trip.** Each trip keeps its own order, stay notes, nights, calculated arrival and departure dates, and travel connections, so the same city can be a 2-night stay in one trip and a 5-night stay in another. Change them from the trip's page; editing from Destinations has no nights or stay notes. Each trip's estimate for the destination applies the shared rates to that trip's nights, and **In your trips** shows each stay's nights, dates and estimate. In Destinations, totals that need nights wait for a trip, and Church shows unless hidden, without Sunday dates, which come from each trip's stay.
- **Removing.** **Delete** in the [options menu](#destination-options-menu) of a trip's destination card asks you to confirm, and **Remove from trip** then removes only that trip's stay: its nights, stay notes, and connections to and from it. The route reconnects, and the destination stays in Destinations with everything saved for it. Deleting a trip keeps its destinations the same way. Adding the city to the trip again brings the destination back with everything saved for it, as a new stay.
- **Deleting.** The owner of a destination that is in no trip can delete it from its page, after confirming. Deleting permanently removes it with everything saved for it: hotels, activities, restaurants, churches, photos, notes, budget amounts, entry requirements, health and safety, and typical weather with its monthly averages. A destination any trip visits can't be deleted, and its page offers no delete; remove it from each trip first. People a trip is shared with can't delete destinations.
- **Sharing.** A destination added to a trip belongs to the trip's owner, even when someone the trip is shared with adds it. When they add a city the owner already has, the trip visits the owner's destination for it, never one of their own, so everyone with the trip can then see and change what the owner saved for it. People a trip is shared with see the destinations it visits in Destinations, marked **Shared by** the owner, and can change them, including for the owner's other trips that visit them, but **In your trips** lists only the trips they can open.
- **Upgrade.** The schema 21 upgrade combines each owner's existing destinations for the same city into one, keeping each trip's stay, dates and connections; see [deployment](docs/DEPLOYMENT.md#schema-21-shared-destinations-tra-105) for how differing details are combined.

## AI assistants
Travel's designated owner, the Google account named by `TRAVEL_OWNER_EMAIL`, can connect ChatGPT and Claude to Travel's MCP endpoint, `/api/mcp` (TRA-115). Each assistant reads all of Travel and proposes changes; nothing changes until the owner approves a proposal on Travel's own page. **AI assistants** in the header, shown only to the designated owner, has the endpoint's address, the connections and the latest proposals. Anyone else finds no such page.

- **Connecting.** Add Travel as a custom connector with the endpoint's address: in Claude, Settings → Connectors → Add custom connector; in ChatGPT, a custom app or connector with developer mode on and OAuth authentication. The assistant registers itself with Travel and opens Travel's **Connect** page, where the owner chooses **Allow** or **Cancel**. Sign in to Travel in that browser first: after signing in, Travel opens All trips, not the Connect page, so start connecting again. Only the designated owner can allow a connection; anyone else signed in is told so. Travel sends authorizations only to Claude's and ChatGPT's own OAuth callbacks, so no other app can be connected. Each Allow makes a separate connection.
- **What assistants read.** Every trip, destination and account, whoever owns them: trip details with their headline images and best time to go, owners and sharing, tags, stays, travel with its layover plans, At home items, packing lists, budgets, destinations with their ideas, churches and their coordinates, research and photos, and each account's email, Google name and whether it has signed in. Never Google account identifiers, sessions, or any code or token.
- **Proposals.** An assistant proposes up to 50 of the planner's own changes at once, with a summary of up to 200 characters. They may apply to any trip or destination, whoever owns it, including deleting trips and changing who they are shared with, and they follow the same rules as editing in Travel. A trip or destination an assistant adds belongs to the designated owner. A change takes only the fields Travel offers for it, below; any other, such as an owner, a creation time or a calculated date, is refused, naming the field, as is a value of the wrong kind. Coordinates change only with coordinate changes, photos only with photo changes, and trips' headline images only with headline image changes, below. Each person's trip order is their own, so assistants can't propose one (TRA-16), and each person likes items themselves, so assistants can't like anything (TRA-31). A change that adds a trip, idea, church, At home item or packing item names it with a new ID, so later changes in the same proposal can change it; a city added to a trip gets its IDs only once approved. A proposal the rules refuse is never recorded, and the assistant is told which change was refused and why.
- **Photos.** An assistant can propose photo changes for destinations, hotels, activities, restaurants and churches (TRA-122): adding photos from the addresses of image files, removing saved photos, choosing the primary or main photo, and, for a destination, putting its photos in order. A destination's primary photo is its headline image, which its page shows first and its card in Destinations shows across its top, so an assistant adds, replaces or removes it with a photo change; removing it makes the first remaining photo primary, as the photo editor does. A photo change for an idea or church keeps its photos' saved order, with new photos last, though its editor can arrange them (TRA-126). A photo change changes nothing but photos, follows the same rules as the photo editors, up to 10 photos each, and can name an idea or church an earlier change in the same proposal adds. It can't choose a destination photo's focal point, which only the photo editor does (TRA-53): saved photos keep theirs, and the photos it adds start centered. Travel downloads each new photo as it is proposed, only over HTTPS and only from public internet addresses: never from private, loopback or link-local ones, checked for the address given, for each of up to 3 redirects, and for every address a host name resolves to as Travel connects. A proposal downloads at most 10 new photos and 15 MiB, up to 5 MiB each, within 15 seconds, and each is then checked and prepared as an upload is (see [Images](#images)). If any photo can't be downloaded or used, nothing is proposed, and the assistant is told which change, which address and why. A proposal's photos are kept beside it, never in a gallery, until it is decided: approving saves them, and rejecting or a failed approval discards them. An expired proposal's photos are deleted with the next proposal or decision.
- **Trip headline images.** An assistant can propose adding, replacing or removing a trip's [headline image](#trip-headline-images) with `trip.image`, which changes nothing else of the trip (TRA-174). It reads each trip's image, its version and crops, and sees the image itself by its version. A new image comes from the address of an image file, downloaded, checked and prepared as an assistant's photos are, within the same limits, which it counts toward, and saved as the trip editor saves an upload, with its large version. It replaces any saved image and starts uncropped, centered at 100% on the trip's card and banner, as a new image does in the trip editor, where only people crop it. A trip a proposal adds can get its image in the same proposal. Only proposals make these changes; people change a headline image in the trip editor, as before.
- **Editable fields.** Each record's ordinary fields, single values such as a trip's tagline, a destination's budget amounts or a flight's airline, are declared once, with their kind, limits, label and description, in `src/lib/editable-fields.ts` (TRA-174). People's saves and assistants' proposals are checked by those same rules, assistants are told about each field from there, and the proposal's page labels it from there, so a field added there is read, proposed and reviewed with no code of its own for assistants. Lists, records of their own, IDs, photos and every other change keep explicit support, and nothing outside these can be proposed.
- **Coordinates.** An assistant can propose coordinates for hotels, activities, restaurants and churches, so they show on their destination's map when their addresses can't be found or they have none (TRA-150, TRA-163): `candidate.coordinates` and `church.coordinates` each set one place's latitude, longitude and accuracy, exact or approximate, or remove them, and change nothing else of it, so a proposal never resends its address, price, notes or anything else. One proposal can place up to 50 places. The proposal's page shows each place's **Latitude**, **Longitude** and **Coordinates accuracy**, before and after, and each change's title says whether it sets exact or approximate coordinates. An idea or church a proposal adds gets its coordinates from a later change in it. A change to a place's address, from an assistant or in Travel, leaves its saved coordinates waiting for review, which the proposal's page shows as **Coordinates to review**, until coordinates are set for it again or removed. Assistants read every place's coordinates, and whether they wait for review. Travel checks only that coordinates are in range: never whether they are right, so an assistant should give only coordinates from a source it can name.
- **Reviewing.** The assistant gives the owner a link to the proposal's page, which lists each change and every record it adds, changes or deletes, field by field, before and after, including what follows from it, such as travel connections cleared by a new city or an email authorized by sharing. A destination's monthly averages show as their source, reference years and each month, every one listed with the saved value beside the proposed one (TRA-158). While the proposal waits, each photo it adds, changes or deletes appears beside its record, with its order and whether it is the primary or main photo, and a trip's current and proposed headline images appear side by side, labeled **Current** and **Proposed**; only the owner can see them. In windows up to 640 pixels wide, such as phones, each field stacks its name above its Before and After values, each labeled, in place of the Field, Before and After columns wider windows show (TRA-121). The whole proposal then reads without scrolling sideways down to 320 pixels: long text, links and values of several lines wrap, and photos shrink to fit, keeping their shape. The two decision buttons are at least 44 pixels tall, and on phones the page ends with room for Send feedback, so at the end of the page they sit above it. **Approve every change** makes all of them in one transaction, exactly as shown, or none: if Travel has changed since in a way that would make a change do anything else, or a rule refuses one, nothing changes and the proposal fails with the reason. **Reject** changes nothing. Each proposal is decided once, within 24 hours, after which it expires. A database failure while approving, such as a full disk, also changes nothing, and leaves the proposal to approve again. The assistant reads what became of it.
- **Ordinary access is unchanged.** An assistant's reach comes only through the owner's approval of each proposal; what each signed-in account can open and change in Travel itself stays as described above. People change photos only in Travel's photo editors, never with photo changes, and coordinates only in each place's editor, never with coordinate changes.
- **Connections.** An assistant's access lasts an hour at a time and is renewed with a single-use refresh token; a connection not renewed for 30 days ends. **Revoke** in AI assistants ends a connection at once and withdraws its proposals. Starting Travel with a different `TRAVEL_OWNER_EMAIL` ends the previous owner's connections. Codes and tokens are stored only as hashes, as sessions are. Registrations never allowed are removed after a day, and at most 100 can wait at once.
- **Upgrade.** Schema 24 adds the connection and proposal tables and changes no trip (see [deployment](docs/DEPLOYMENT.md#schema-24-chatgpt-and-claude-connections-and-proposals-tra-115)). Schema 25 adds the table for proposals' photos and changes no trip or photo (see [deployment](docs/DEPLOYMENT.md#schema-25-photos-proposed-by-chatgpt-and-claude-tra-122)).

The container smoke script needs Docker and Bash. It builds the image and checks the container, persistent storage, sign-in enforcement, the refusal to start with a database it can't open or upgrade, the health check deploys wait for, trip and destination isolation, that only the designated owner reaches AI assistants and their proposals' photos and only an access token reaches the MCP endpoint, and that every image format uploads take decodes in the built image (TRA-179), which a Next.js build alone does not verify.

After building, CI also runs `node scripts/review-errors-smoke.mjs` to check production page status codes, failure recovery, and save validation with health-, image-, and page-first store initialization, and connecting Claude, from registration and the owner's consent to MCP reads, a proposal, its approval and revoking the connection. It also checks photo proposals: refusing photo addresses on private networks, showing a proposal's photos to the owner alone, and approving and rejecting photo changes. And it checks that a trip's headline image is served only to the accounts that can open the trip, as sharing and unsharing change who they are, and that a save naming an image without the trip editor's form changes nothing (TRA-133), and that **Add image by URL** refuses signed-out requests, other sites, addresses that aren't `http://` or `https://`, and private addresses, given by IP address or by name (TRA-139). It previews a HEIC photo as a photo editor asks, decoded by the production build, and checks the preview refuses signed-out requests, other sites and an image saving would refuse (TRA-179). No public image server is reachable there, so the proposal that adds a photo is made through the store with a photo prepared as a download would be. It creates disposable databases and logs under `test-results`, using fixture sessions without contacting Google. You can run the same command locally.

## Local production preview
`pnpm build` produces Next.js standalone output, the same server the Docker image runs. Next.js warns that `next start`, which `pnpm start` runs, does not work with standalone output. To preview a build, copy in the files the standalone server leaves out, then start it with your `.env.local` settings:
```sh
pnpm build
cp -r public .next/standalone/
cp -r .next/static .next/standalone/.next/
TRAVEL_DATABASE_PATH="$PWD/data/travel.sqlite" node --env-file=.env.local .next/standalone/server.js
```
Repeat the copies after every build. The standalone server doesn't read `.env.local` itself, so `--env-file` passes your sign-in settings. It runs from `.next/standalone`, so `TRAVEL_DATABASE_PATH` must be absolute; a relative path would create a new, empty database inside the build output. The value on the command line takes precedence over the one in `.env.local`. The Docker image instead starts through `scripts/start.mjs`, which refuses to start without mounted persistent storage and opens and upgrades the database before the server starts (see [Hosting](#hosting)).

Trip and destination pages fetch only the relevant trip's or destination's data. Home-page budgets are computed on the server and reused while searching, and saves refresh the displayed page without returning the entire database to the browser. ## Travel 1.8 review fixes
Save failures keep their specific validation message even when an API route opens the database first. Unexpected failures retain the generic save error.

City suggestions limit upstream requests within the single application process to 300 per rolling minute, 2,500 per hour, and 8,000 per day, with at most eight concurrent requests. An anonymous client cookie provides best-effort limits of 20 upstream requests per minute and two concurrent requests per client. An upstream rate-limit response pauses new lookups for 60 seconds. Cached suggestions remain available; manual city entry still works when new suggestions are temporarily unavailable. These in-memory limits reset when the process restarts.

Feedback errors appear only when there is a message. Unreadable server responses show the standard friendly error, and **Send** can retry failed initialization without closing the sheet or losing the draft, unless Travel refused it with HTTP 429 (see [Feedback](#feedback)). Pending submissions still prevent duplicate sends.

The error page's **Try again** reloads failed server data. Initial requests for missing trips, destinations, or categories return HTTP 404; server-rendering failures return HTTP 500. Pages wait for their server checks before sending a response, instead of streaming the root loading screen first.

## Trip dates and nights
Set the trip's optional **Start date**, then enter each destination's nonnegative whole number of **Nights** from the trip's page. Nights and stay notes belong to the trip, so a destination shared with other trips can have different nights in each. Arrival and departure dates, their weekdays, and the trip end date are calculated in destination order. A departure is the next destination's arrival, unless the connection between them has [nights spent traveling](#nights-spent-traveling), each of which moves the arrival a day later, as one on the way home moves the trip end; changing the start, nights, nights spent traveling, or order recalculates the route. A zero-night stop arrives and departs on the same day. Dates cannot be overridden individually. Travel-leg timing notes do not determine the schedule.

Missing start dates or night counts leave affected dates and the trip end incomplete. Earlier complete destinations retain their calculated ranges. Nights still drive budget estimates even when the trip start is unknown. Stay notes and the trip's flexible date label remain descriptive text and are never parsed.

Schema 15 preserves original arrival/departure values separately. It backfills only valid, consistent structured dates; gaps, overlaps, invalid dates, and incomplete chains require review. Preserved dates appear beside incomplete schedules so you can set the start and nights deliberately. Migration replay retains later edits. See [deployment and rollback](docs/DEPLOYMENT.md) before upgrading.

## Nights spent traveling
A travel connection can take nights of its own, such as an overnight flight, a night train or a cruise, apart from every destination's nights (TRA-185).

- **Entering.** In **Plan this connection**, **Nights spent traveling**, below **Departure** and **Arrival**, is how many nights are spent on the way: 1 for an overnight flight, 2 for a two-night cruise. It is a whole number from 0; left blank it saves 0, and a negative or fractional number is refused with *Nights spent traveling must be a whole number between 0 and 3652058.*, changing nothing. Every connection starts with 0, existing ones included. Travel never works them out from a flight number, times or time zones: they are only what you enter.
- **Days and dates.** Each one moves the rest of the trip a day later: the next destination's arrival and departure, every later date, and the trip end, which the connection home moves alone. The start date stays the trip's first day, and every destination keeps its nights. With a start date, a save that would take the trip past December 31, 9999 is refused, even before a destination whose nights aren't set.
- **No cost.** They are no destination's nights, so hotel nights, daily food and miscellaneous days, the connection's price and spending in transit, every destination's budget and the trip estimate are unchanged. They add no cost and no budget category.
- **On the trip page.** The connection's card in **Between the places** names them after its transportation and times, such as *Flight · 1 night spent traveling*, and **Clear** shows for a connection with only them. The [Calendar](#trip-calendar) shows each of their nights as spent traveling.
- **What changes them.** Saving the connection's other details keeps them, as does a save from a page opened before them, which doesn't send them. **Clear** sets them back to 0 with the rest of the travel plan, as does a route or city change that clears or replaces the connection, and the dates follow.
- **Sharing.** They belong to the trip, so everyone who can open it sees and changes them, and no one else. ChatGPT and Claude read them with the trip's travel and can propose them with a connection's other details, which the proposal's page shows as **Nights spent traveling**, with the arrival and departure dates they move.
- **Upgrade.** Schema 52 starts every existing connection with 0, so no trip's dates or estimate change (see [deployment](docs/DEPLOYMENT.md#schema-52-nights-spent-traveling-tra-185)).

## Trip calendar
Each trip's page has a **Calendar**, below **Between the places** and above **Best time to go**, that lists the trip day by day: **Day 1**, **Day 2** and on, whether or not it has dates yet (TRA-185). It is read only, the same for everyone who can open the trip, and worked out from the trip's saved destinations, their nights and its connections' [nights spent traveling](#nights-spent-traveling); nothing is saved for it.

- **Days.** Day 1 is the day the trip leaves its departing city. With a start date, each day's heading shows its date beside its number, such as *Day 1, Sat, Jun 5, 2027*, and the destinations' dates and the trip end fall on the same days. Without one, days have numbers alone, and the section says to add a start date in **Edit trip** to see their dates.
- **What happens.** Each day lists, in travel order: a connection leaving, by its transportation and route, such as *Flight: Boston → Paris*, with its nights spent traveling and the day it arrives; *Still traveling* for a whole day on the way; *Arrive in* a destination as its stay of so many nights begins; *In* a destination for a whole day there; *Depart* a destination; *Visit* a destination for a same-day visit, with no nights; and on the last day, *Arrive in* the return city at the end of the trip. Connections and the departing and return cities are named as **Between the places** names them. A connection without nights spent traveling arrives the day it leaves, so departing one destination and arriving at the next share a day: arriving on Day 2 for three nights departs on Day 5.
- **Nights.** Every day but the last ends with its night, numbered as the day: *Night 2: Paris*, with the destination's chosen hotel as *Chosen stay* once one is chosen, or *Night 1: Spent traveling* with the connection, on a warm background with an orange edge, apart from destinations' nights. Each night is spent at one destination or traveling, never both, so nights spent traveling are never a destination's.
- **Missing nights.** The calendar ends on the day it arrives at the first destination whose nights aren't set, whose night says *Not known yet*. It then says that destination has no nights set yet, so the rest of the trip has no days, and lists the rest of the route in travel order, each connection with its nights spent traveling and each destination with its nights, without days or dates. Nothing is guessed: setting the nights gives them their days.
- **Updates.** It follows every saved change as the page loads again: destinations added, removed or moved, their nights, nights spent traveling, the start date and the cities.
- **Long trips.** It lists at most the first 366 days, a year with a leap day, and then says how many more days follow.
- **Empty.** A trip without destinations says its days will appear once you add a destination.
- **Phones and screen readers.** Each day is a box with its heading beside its lines on wider screens, and above them on phones, where it has 12 pixels of padding and the section is 28 pixels from the next, as the trip page's other sections are (TRA-156). Text wraps within the screen, so the page never scrolls sideways. Each day's heading is a heading, with its date read after its number, and every line has at least 4.5:1 contrast.
- **Not included.** Month, week or grid calendars; times or days for activities, restaurants or tours; calendar sync, printing or exports; flight schedules, detecting overnight travel or time zones; booking hotels or assigning them to nights; costs for overnight travel; and moving anything from the calendar, which only reflects the trip's plan.

## Budget rules
Every price is in **USD**, for the entire traveling party, with at most two decimal places. Currency selectors have been removed. Existing USD amounts retain their exact cents. Startup stops on unexpected non-USD records without converting or relabeling them; review those records before deployment.

Every amount follows the same rules, from destination budgets, connections' miscellaneous spending and trips' entry and visa fees to the estimated prices of ideas, travel connections and at-home tasks: zero or more, at most two decimal places, and no more than $100,000,000. An amount outside them is refused with the same message in every field, naming that field. A subtotal too large to calculate exactly shows as not estimated, never as an inexact amount.

A destination's amounts, rates and methods are shared by every trip that visits it, and each trip's estimate uses its own nights. The estimate sums every travel leg and its miscellaneous spending in transit, the trip's entry and visa fees, one selected hotel or the general nightly estimate per destination, the selected activities and food methods, miscellaneous spending at destinations, shopping, and entered at-home expenses. Alternatives stay saved without contributing, as do a flight's [miles required](#miles-required), which are never money. Missing required amounts remain visibly unknown; zero is known. At-home, shopping, transit miscellaneous and entry and visa fee amounts are optional: blank adds no cost and does not make a complete estimate partial. The departing city is optional and is not an amount, so leaving it blank never makes an estimate partial; the travel from and to it is priced and counted like every other connection (TRA-85).

On a trip's page, **The trip estimate** shows the total and who it is for, each category's amount, and whether every required estimate is added, below its heading. The ROOM IN THE BUDGET label that was above the heading is removed, with its space, on desktop, tablets and phones (TRA-149). It had no amount of its own, so no amount or calculation changes. The estimate ends with whether every required estimate is added: the paragraph that followed, listing what the estimate includes, is removed to keep the estimate focused on its amounts and categories (TRA-151); this section describes what it includes.

Changing a destination, departing city, or effective return city clears only affected travel plans, including [airline and flight number](#airline-and-flight-number), [miles required](#miles-required), miscellaneous spending, [nights spent traveling](#nights-spent-traveling), links, itinerary and [layover plans](#layover-plans); renaming a destination clears them in every trip that visits it. Reordering destinations keeps unchanged connections.

## Entering missing amounts
On a trip's page, each **Not set** and **Not estimated** amount in **The trip estimate** and in each destination card's **Budget** is a link that opens the existing editor for that amount, with its field focused and ready to type in (TRA-165). In the trip estimate, so is a category's count of estimates still missing, such as **2 not estimated** beside a partial amount. The trip estimate opens the category's first missing amount in route order: the connections from the departing city to the return city, then each stay in turn. A destination card opens its own.

- A connection's price, or for **Transit miscellaneous** its miscellaneous spending, opens **Plan this connection**.
- **Entry / visa fees** opens **Edit trip** at its amount (TRA-159).
- A hotel chosen for the budget, or an activity or restaurant included in itemized costs, that has no price opens its own editor at its price.
- A destination's amount opens its budget editor, titled with the destination, such as **Edit accommodation budget for Vienna**: Accommodation's nightly amount, the general activities amount, the daily food amount, the shopping amount or the daily miscellaneous amount. Once a nightly or daily amount is entered, the stay's nights it waits for open in Accommodation's editor, or otherwise in **Edit destination nights**.

Each editor shows what is saved, and nothing is saved until you save it. Saving updates the amounts, the counts of what is missing and the totals as any save does; **Cancel**, the X and Escape change nothing. A saved $0 is an amount, not **Not set**, so it isn't a link, and At home has nothing to enter, since a blank price there adds no cost. The links are underlined in Travel's green, as research links are, at the size of the amounts they show: Tab reaches them, Enter or Space opens them, and on touchscreens each is 44 pixels tall. If a save replaces a link while it has keyboard focus, the trip estimate's heading, or the card's **Budget** heading, takes focus. A destination's own page, where nights belong to each trip, shows these amounts as text, as before.

## Daily miscellaneous spending
Enter a daily miscellaneous amount in the destination editor or with **Edit miscellaneous budget**. The subtotal is daily amount × nights, except a **zero-night stop uses one full budget day**. For example, three nights uses three days, one night uses one day, and zero nights also uses one day. The preview updates as nights and the amount change. Missing nights or amounts keep the estimate partial, including a zero amount with unknown nights. Clearing the amount marks it unknown.

## Nightly hotel estimate
Enter a general nightly amount in the destination editor or from Hotels. Its subtotal is nightly amount × nights; a zero-night stay costs zero when its rate is known. Unknown nights or a missing rate remain unestimated.

With no hotel selected, the general estimate supplies accommodation. Selecting a hotel replaces it with that hotel's whole-stay price, counted once. A selected hotel with an unknown price keeps accommodation unknown. Selecting, editing, unchecking, or deleting hotels preserves the general estimate; removing the selection restores it using the current nights.

## Activities budget
Choose **General budget** or **Itemized activity costs** in the destination editor, with **Edit budget** in a destination's Activities section, or on its Activities page. Itemized is the default. A general amount covers the whole stay once; nights and travelers never multiply it. Missing amounts keep totals partial only in General budget mode.

Itemized mode uses only included activities, with included missing prices keeping the estimate partial; no included activities contributes zero. Switching methods preserves the general amount, saved ideas, and selections. Editing ideas never switches the method.

## Food budget
Choose **Daily food budget** or **Itemized restaurant costs** in the destination editor, with **Edit budget** in a destination's Restaurants section, or on its Restaurants page. Itemized is the default. The daily amount uses the same duration as miscellaneous spending: nights, with **one full day for a zero-night stop**. Missing rates or nights are unknown, even for a zero rate, and make totals partial only in daily mode.

Daily mode excludes restaurant costs. Itemized mode counts only included restaurants' whole-party meal prices, with included missing prices keeping the estimate partial. No included restaurants contributes zero. Switching methods preserves entries, selections, and the daily estimate. Traveler count never multiplies amounts.

## Shopping budget
Use the edit control beside **Shopping**, or edit the destination, to enter an optional whole-stay amount. It is counted once, separately from miscellaneous spending. **Not set** adds no cost and is not a missing estimate. Zero is an intentional known amount. Clear the amount to remove its contribution.

## Miscellaneous spending in transit
Each travel connection's editor, **Plan this connection**, has an optional **Miscellaneous spending (USD)** field for spending on the way, such as airport meals, drinks, snacks and layover purchases (TRA-26). One amount covers the whole connection, layovers and stops included, for the whole party; travelers never multiply it. Use the connection's **Notes** for what it covers. Blank adds no cost and is not a missing estimate; zero is an intentional known amount. Its field has no increment and decrement arrows, as the price's has none.

A connection with an amount shows it on its card in **Between the places**, below its transportation price, as **Miscellaneous spending**. The trip estimate's **Transit miscellaneous** row totals every connection's amount, separately from **Travel** and the destinations' **Miscellaneous**, and the total counts it once; the row shows **Not set** while no connection has an amount. Saving the connection keeps its amount, as does a save from a page opened before this field existed, which doesn't send it. **Clear** clears it with the rest of the travel plan, and a route change that removes or clears a connection takes its amount out of the estimate. ChatGPT and Claude can propose it with a connection's other details. Schema 29 adds it to each connection, blank (see [deployment](docs/DEPLOYMENT.md#schema-29-miscellaneous-spending-in-transit-tra-26)).

## Entry and visa fees
Each trip can have one optional estimate of its **entry and visa fees**, such as visa applications, electronic travel authorizations and entry fees, in USD for the whole party and every destination (TRA-159). Enter it in **Edit trip**, in **Entry / visa fees (USD, optional)** beside **Travelers**, or select **Not set** beside **Entry / visa fees** in **The trip estimate**, which opens Edit trip with the amount ready to type in. It follows the same rules as every other amount, and its field has no increment and decrement arrows.

**The trip estimate** shows it as **Entry / visa fees**, after **Transit miscellaneous**, and counts it once in the total, as does the trip's card on All trips. Travelers and destinations never multiply it, and no destination's budget includes it. **Not set** adds no cost and is not a missing estimate, so a trip without it keeps its total and stays complete; zero is an intentional known amount. Clear the amount to remove it. It is one combined amount: fees aren't tracked per traveler, destination or visa, Travel never calculates them from citizenship, destinations, travelers or visa types, and [entry requirements](#entry-requirements) research is unchanged.

Saving the trip keeps its amount, as does a save from a page opened before this field existed, which doesn't send it. ChatGPT and Claude read it with the trip and its budget, and can propose it with the trip's other details, which the proposal's page shows as **Entry / visa fees**. Schema 46 adds it to each trip, not set, so no trip's estimate changes (see [deployment](docs/DEPLOYMENT.md#schema-46-trip-entry-and-visa-fees-tra-159)).

## Destination options menu
Each destination card on a trip's page has one options button, three dots at the right of its name, where its arrows, pencil and trash can were (TRA-55). Screen readers hear it as **Options for** and the destination, named as its card names it. It opens a menu of **Move up**, **Move down**, **Edit** and **Delete**, in that order, each with its icon:

- **Move up** and **Move down** move the destination one place earlier or later in the trip, as the arrows did. They save at once, and the trip's travel connections follow the new order as before, keeping those that don't change. **Move up** is disabled for the first destination and **Move down** for the last, so a trip with one destination has both disabled. Disabled actions still show.
- **Edit** opens the destination's complete editor, as the pencil did.
- **Delete** opens the confirmation the trash can opened: **Remove from trip** removes only this trip's stay, and the destination stays in Destinations with everything saved for it (see [Destinations](#destinations)). **Cancel** changes nothing.
- **Opening and closing.** The menu opens below the button, or above it when it doesn't fit below and there is more room above, lined up with the button's right edge, so it stays within the window and the page never scrolls sideways. Selecting an action closes it, and so do a click or tap outside it, Escape, the button again, and opening another destination's menu.
- **From the keyboard.** Enter or Space on the button opens the menu with focus on its first action that isn't disabled. The Up and Down arrows move between those actions, wrapping around at either end, Home and End go to the first and last, and Enter or Space selects one. Escape, or the button again, closes the menu with focus back on the button; Tab closes it and moves on to the next control.
- **Focus after an action.** Once the page shows a move, focus is on the destination's options button in its new place, so Enter opens its menu to move it again. **Edit** and **Delete** move focus into their editor or confirmation, which return it to the options button when they close, unless the destination was removed.
- **While saving.** The options button and every action are disabled while a change saves, so nothing saves twice.
- **Touchscreens.** The button and each action are 44 pixels tall.
- **Unchanged.** Everything else on the card, from its name, tagline, stay notes and Like to its photos, map, budget, ideas and research, and the controls for hotels, activities, restaurants, churches, travel and the rest of Travel.

## Destination controls
Each destination's **Budget** starts collapsed each time the page loads. It always lists Accommodation, Activities, Food, Shopping, and Miscellaneous with their amounts, with **Edit shopping budget** and **Edit miscellaneous budget** beside Shopping and Miscellaneous. The Hotels, Activities and Restaurants sections below it change Accommodation, Activities and Food, so the budget no longer links to those pages (TRA-120). Activities or Food with some included prices missing show **Partial estimate**. On a trip's page, the stay's nights, arrival, and departure sit above it and the destination estimate below. Adding a city to a trip again, from any editor, shows the stop the first save added instead (TRA-107).

It stays until you dismiss it or start another change.

A destination's **Move up** and **Move down** return focus to its options button in its new place, so Enter opens its menu to move it again (TRA-55). A failed change leaves focus on its control. If you move focus elsewhere while a change saves, it stays where you put it.

Screen readers hear the names and headings the page shows (TRA-95). Where a connection's card and editor show an arrow between its places, they read "to", as in **Wooster, Ohio to Rome, Italy**. **Edit shopping budget**, **Edit miscellaneous budget**, **Show Church** and the **Churches** section name their destination as its card does, so a city chosen from a suggestion is **Paris, France**, not its saved label. An idea's **Must do** control is named by the label it shows, **Mark as must do** or **Must do**, followed by the idea's name. An idea's star in a destination's carousel shows no label, so it is named **Must do for** and the idea's name, and says whether it is pressed (TRA-161, TRA-181). Below each card's **Churches** heading, the Sundays during the stay are a heading one level down, and below the **Church** heading of a destination's Church page, so are each church and the message shown without any, with each church's Mass times one level below its name, so the headings nest in order. Nothing on screen changes.

Each section's edit control opens an editor titled for that section with only its fields, while **Edit destination** in Destinations and **Edit** in each trip destination card's [options menu](#destination-options-menu) still open the complete destination editor (TRA-113). On Hotels, **Edit estimate & nights** opens the stay's nights and the general nightly estimate, with previews of the stay's dates and estimate; in Destinations, where nights belong to each trip, **Edit nightly estimate** opens the nightly estimate alone. The Hotels section's **Edit budget** opens the same editor, and the Activities and Restaurants sections' open the activities and food budget editors. **Edit miscellaneous budget** opens the daily miscellaneous amount, previewed with the stay's nights. Closing the dialog, or deleting an activity from it, discards every activity's unsaved changes. The editor doesn't swipe, since its fields keep their own sideways gestures. Adding one shows no Delete. **Delete** never saves the draft: it opens the confirmation the category's page shows, which names the idea, says it will be removed from the destination in every trip that visits it, and warns that this can't be undone. ## Health and safety
Each destination card, and each destination's page in Destinations, has a **Health and safety** section for manually maintained research, separate from **Entry requirements** (TRA-14). Record the destination's local emergency number; the government travel advisory level and its warnings; health precautions such as recommended vaccinations and medical precautions; local safety concerns, common scams, areas to avoid, and general safety guidance; emergency contacts; official source links with descriptions; and the date you last checked the information. All fields are optional. Unrecorded fields show **Not recorded**, and the section notes that missing information does not mean the destination is safe or that no precautions are needed.

**Local Emergency Number** comes first in the section, above everything else, whether the section is open or closed (TRA-173). Once verified, it shows the destination's primary emergency number, such as 112 in much of Europe or 911 in the United States, in large bold text, with a **Call** button, such as **Call 112**, that opens your phone's or computer's dialer with the number, and below them the date it was verified and its source, a link that opens in a new tab. The box has the plain border and white background of the section's other information, its heading is in Travel's usual text color, and **Call** is Travel's ordinary secondary button, with no red, so the number reads as reference information rather than a warning (TRA-183). Travel never places or completes the call itself. Without a verified number, the box's heading is muted and it says **Emergency number not verified**, with nothing to call, whether or not other research is recorded. On phones the Call button sits below the number across the box, at least 48 pixels high. In the Health and safety editor, **Local emergency number** comes before the emergency contacts: enter the number, the address of the official or reliable page that gives it, such as a government, embassy, or emergency service page, and the date you verified it there. All three are needed together, so a number is never saved or shown unverified, and clearing all three removes it. Travel never looks a number up, assumes one from the country, or takes one from the emergency contacts, which stay as they were; put other emergency numbers, such as a separate ambulance number, in the emergency contacts. Saving, changing, or clearing the number changes nothing else in the research.

**U.S. travel advisory level** is the editor's first field, a dropdown of the U.S. State Department's four levels with their official descriptions, **Level 1: Exercise Normal Precautions**, **Level 2: Exercise Increased Caution**, **Level 3: Reconsider Travel** and **Level 4: Do Not Travel**, and **Not set** (TRA-171). It starts Not set, so a destination never shows a level nobody chose; leave it Not set until you have checked the current advisory. Once the section is open, its first line shows the chosen level in its color, green for Level 1, yellow for Level 2, orange for Level 3 and red for Level 4, always with its number and description, so it reads the same without color; with none chosen it shows **Not recorded**. It is separate from **Travel advisory level**, which keeps the advisory level as typed: Travel never reads a level from your research or looks one up. Choosing, changing, or setting it back to Not set saves with the rest of the editor and changes nothing else, and **Clear** removes it with the record. An editor on a page opened before the dropdown existed asks you to reload instead of saving, so it never clears a level chosen since.

Add, edit, or remove up to 20 emergency contacts, each with a name, a phone number, and optional notes. Phone numbers may contain digits, spaces, plus signs, parentheses, hyphens, and periods; put an extension or an alternative number in the notes or in another contact. Sources are up to 20 http or https links with optional descriptions, as in Entry requirements.

**Non-emergency medical care** follows the emergency contacts, apart from them: doctors, medical clinics, and outpatient facilities for routine illness or minor injuries, such as a bad cold, an ear infection, or a sprain (TRA-172). Add, edit, or remove as many providers as are worth keeping in the Health and safety editor, below its emergency contacts. Each needs a name; everything else is optional: its medical specialty or services, phone number, website, address, a map location as a latitude and longitude, notes, up to 20 source links of its own with optional descriptions, and the date you last verified its details. For each provider, record whether a source confirmed that it offers consultations in English and that it sees visiting American patients, **Verified** or **Unconfirmed**, and the soonest visit a source confirmed it offers: **Walk-in visits**, **Same-day appointments**, **Short-notice appointments**, or **Unconfirmed**. A new provider starts Unconfirmed on all three, and whatever you leave blank shows **Not recorded** or **Not verified**; Travel never fills anything in. Prefer providers confirmed to offer consultations in English, starting with the U.S. embassy's or consulate's list of medical providers, then the provider's own website and other reliable sources, and save the pages you used as its sources.

Once the section is open, providers verified to offer consultations in English come first, each group in the order saved. Each shows its name, its specialty or services, the three checks, when it was last verified, its phone number as a link that calls it, its website, its address and its map location as links that open Google Maps in a new tab, its notes, and its sources. A verified soonest visit reads, for example, **Walk-in visits (verified, not guaranteed)**. The subsection says it is for routine care, not emergencies, in which you call local emergency services or the emergency contacts; that verified means a source confirmed it when the provider was last verified, never a guaranteed appointment, so call ahead; and that appearing on a U.S. embassy or consulate list of medical providers does not mean the U.S. government endorses or guarantees a provider. The details share two columns on wider screens and stack on phones, and the links that call, open the website and open the map are at least 24 pixels high. Travel never finds or ranks providers, checks their details or availability, books appointments, handles insurance, or gives medical advice, and it never looks an address or map location up.

The section starts collapsed each time the page loads, showing only its **Health and safety** heading and its local emergency number, and **Add health and safety** while no research is recorded. Select the heading by mouse, touch, or keyboard to show or hide the reminder to verify before traveling, the recorded research, emergency contacts, non-emergency medical care, sources, and last checked date, with **Edit health and safety** and **Clear** beside the heading once research is recorded (TRA-148). Each destination's section opens and closes on its own, showing or hiding its buttons at once, and **Add health and safety** works either way. If a save hides the button with keyboard focus, as adding research in a collapsed section does, focus moves to the heading. Showing or hiding changes nothing saved, makes no server request, and is not remembered between visits.

The last checked date is only what you enter: saving never sets or changes it, and Travel never marks research as outdated because of its age. Verify advisories, health guidance, and contacts with official sources before traveling. Travel does not retrieve advisories, health information, emergency numbers, or emergency contacts, monitor them for changes, or give medical advice. **Clear** removes the record after confirmation; Cancel discards an editor draft. Research is stored with the destination (schema 22, the U.S. travel advisory level since schema 44, which starts every existing record Not set, medical providers since schema 45, which starts every existing record without any, and the local emergency number since schema 47, which starts every existing record not verified), shared by every trip that visits it, kept when dates or other destination details change, included in backups, and kept when the destination leaves a trip or its trip is deleted. Everyone who can open the destination sees its emergency number and can change it. **Clear** removes the providers and the emergency number with the rest of the record, and an editor on a page opened before providers or the emergency number existed asks you to reload instead of saving, so it never removes what was added since. ChatGPT and Claude read the level, the providers and the emergency number with the rest of the research and propose them the same way, always giving a level or none, the providers, or none, and the emergency number with its source and verified date, or none (see [AI assistants](#ai-assistants)).

## Typical weather
Each destination card on the main trip page, and each destination's page in Destinations, shows **Typical weather**, with **Edit typical weather** while it's open. Category detail pages do not repeat it. Enter optional high and low temperatures in °F, rainfall notes, the month or period described, and a source name or link. These are manually recorded typical conditions; there is no automatic lookup or Celsius conversion.

The section starts collapsed each time the page loads, showing only its **Typical weather** heading. Select the heading by mouse, touch, or keyboard to show or hide **Edit typical weather** beside it (TRA-148), the temperatures, period, rainfall notes, source, and explanation, and the monthly averages below them with their own buttons. Each destination's section opens and closes on its own, showing or hiding its buttons at once. Showing or hiding changes nothing saved, makes no server request, and is not remembered between visits.

Negative and decimal Fahrenheit values are accepted; high must be at least low when both are supplied. Missing values show **Not provided** and zero shows **0 °F**. Clear individual fields or use **Clear all weather fields** and save. Weather and its recorded period persist independently of schedule and budget changes.

Below them, **Monthly averages** charts the destination's historical climate averages for every month (TRA-135): the average daily high and low in °F as two lines from January to December, over each month's average precipitation in inches as a bar (TRA-164), with a legend naming all three, the averages' source and reference years, and **Every month as a table**. They are typical conditions from past years, never a forecast. Every destination uses the same chart with its own averages.

- **Recording them.** **Add monthly averages**, or **Edit monthly averages** once some are saved, asks for each month's average high and low in °F and average total precipitation in inches, the source's name or link, and the first and last reference years, such as 1991–2020. Every value is required, and Travel never looks averages up, estimates them or fills in a missing month. Temperatures are from -150 to 150 °F, with each month's high at least its low; precipitation is from 0 to 200 inches; years have four digits, the first no later than the last. Saving replaces the saved averages, and **Clear** removes them with their source and years after confirming. A destination without averages says none are recorded and charts nothing.
- **Exploring months.** Hover over a month, tap anywhere in its column, drag a finger or pressed mouse across the months, or reach the months with Tab and move between them with the arrow keys, to show a month's average high, low and precipitation below the chart. Screen readers read each month's averages as it is chosen. Choosing a month changes only what the chart shows: nothing is saved, and trip dates and averages stay as they are.
- **Precipitation.** Each month's bar stands in its month's column and rises from 0 on its own axis at the right, labeled in inches, while temperatures keep theirs in °F at the left (TRA-164). The inches axis reaches the wettest month in as many steps as the °F axis has, so the two share every gridline. A month saved with 0 inches has no bar and reads **0 in** when chosen and in the table; since every month's precipitation is required, no bar is ever missing or estimated. The bars are a lighter blue than the lows' line, drawn over the gridlines and under the temperature lines, which are unchanged.
- **In a trip.** On a trip's page, a stay with dates starts with the month it begins chosen and marked **Your stay begins**, which stays marked when another month is chosen. Without dates for the stay, and on a destination's own page, no month is chosen until someone chooses one.
- **Narrow screens.** The chart fits its card at every width without scrolling sideways, both axes' labels included. Where three letters a month don't fit, as on phones, each month shows its initial and the chart is shorter. Where the table's four columns don't fit, as on 320-pixel phones, the table scrolls sideways within its own box and never reaches past its card (TRA-157).
- **Kept apart.** Monthly averages are saved apart from the typical weather above, so saving or clearing either one, **Clear all weather fields** included, keeps the other, as do date, budget and other research changes. They belong to the destination, so every trip that visits it shows the same averages, and deleting the destination deletes them.
- **From ChatGPT and Claude.** An assistant can propose a destination's monthly averages for the owner to approve (TRA-158): all 12 months in one change, each named once, January to December, in any order, with its average high and low in °F and precipitation in inches, from one source over its reference years, by the same rules as the editor. A proposal missing a month, giving one twice or unnamed, or giving anything else, such as a temperature in °C, is refused with what to fix, and nothing is proposed. The proposal's page shows the averages' source, reference years and every month, beside the saved ones for a destination that has them, every month listed whether or not it changes. Nothing changes until the owner approves: approving replaces all 12 months together in the destination's one record, or nothing, and the chart shows them at once; rejecting keeps the saved averages. Proposing or approving them changes nothing else, the typical weather above included.
- **Upgrade.** Schema 36 starts every destination without monthly averages and changes no typical weather (see [deployment](docs/DEPLOYMENT.md#schema-36-monthly-climate-averages-tra-135)).

## Feedback
**Send feedback** is available across the app in the bottom-right corner. With an editor open it stays there, above the backdrop, and the editor ends above it so neither covers the other. A save's message appears just above it on every screen size, in the same place as the errors of changes made without an editor, so neither covers the other. The message closes after five seconds, or sooner with its X (TRA-84). Feedback opens over the editor, and closing or sending it returns to the editor with its draft and focus kept. Messages allow 2,000 characters. Submission shows a pending state, prevents duplicate clicks, and reports success only after Jira confirms creation. Failures preserve the draft for retry; opening again after success starts a fresh message. When Travel refuses a token or a send with HTTP 429, for example because a limit was reached or the sheet was open for over 15 minutes, **Send** shows **Feedback is temporarily unavailable. Please try again later.** again without asking the server, until the sheet is closed and reopened (TRA-92).

The server creates a Task in the TRA backlog with label `user-feedback`. Its summary uses the first 80 characters of the first message line; its description includes the full message, page path/query, browser user agent, and viewport. Jira calls time out after 10 seconds and are never automatically retried. A delivery that times out may have reached Jira, so a manual retry can create another task.

Set server-only `JIRA_URL`, `JIRA_EMAIL`, and `JIRA_API_TOKEN` in production. Spaces and line breaks around them are ignored. They are never sent to the browser. Sending feedback requires signing in; there is no CAPTCHA. Same-origin checks, a hidden bot field, short-lived one-use tokens, and in-memory limits protect the endpoint. The limits count per signed-in account, so one account can't use up everyone's for the hour (TRA-92): each account gets 20 tokens an hour, one for each opening of the sheet or retry, and 10 sends an hour, and all accounts together get 20 tokens a minute and 120 an hour, and 5 sends a minute and 30 an hour. One account sending 5 messages or opening the sheet 20 times within a minute holds everyone else up until that minute passes. A send doesn't count when Jira certainly created nothing: the settings are missing or invalid, the connection was refused or Jira's host wasn't found, or Jira answered with a 4xx status or 503. A send that may have created a task, such as one that timed out or got another 5xx status, still counts. Limits apply to this app's single process and reset on restart.

Each failed send logs one line saying why, such as `Feedback delivery failed: Jira answered HTTP 401; check JIRA_EMAIL and JIRA_API_TOKEN.`, a missing setting's name, or an invalid `JIRA_URL`. It never logs a setting's value, the feedback, or what Jira sent.

Local testing must use the loopback stand-in, never real Jira:

```sh
node scripts/jira-feedback-stub.mjs
# In another terminal, set these server environment variables, then pnpm dev:
# JIRA_URL=http://127.0.0.1:3010
# JIRA_EMAIL=stub@example.test
# JIRA_API_TOKEN=local-stand-in
```

Development refuses non-loopback Jira URLs. The stand-in validates the issue envelope and returns a synthetic issue ID without sending anything externally. It accepts any issue the app can send, including messages of 1,000 lines, and counts request size in bytes: a request over 256 KiB gets HTTP 413, and malformed JSON or an invalid issue gets 400. Production configuration and a real Jira delivery still require deployment verification.

## Packing list
Each trip has a **Packing list** section below **At home**, even before destinations are added (TRA-18). It is one list for the whole trip: everyone the trip is shared with sees and changes the same items, and nobody else can. Each item has a name, a category, and a quantity for the whole party from 1 to 9,999, shown after its name when it is more than 1. The categories are **Clothing**, **Toiletries**, **Electronics**, **Documents**, **Health and safety**, **Activity-specific gear** and **Other**, and the list shows them in that order, each with its items in alphabetical order and how many of them are packed. Above them it shows how many items are packed of the total and the percentage, rounded down so 100% means every item, with a bar.

- **Packing.** Each item's checkbox marks it packed, or not packed, as soon as it is selected, with no Save. As with other changes made without an editor, it shows what is saved: it changes once the save succeeds, keeps keyboard focus, and a failed save leaves it as it was with the error at the bottom of the screen. A packed item's name is struck through. On touchscreens the checkboxes are 24 pixels and the rows and the pencil and trash can at least 44 pixels high.
- **Editing.** **Add item** adds an item with its name, its category, which a new item chooses, and its quantity, 1 to start; it starts not packed. The pencil changes an item's name, category and quantity and keeps whether it is packed, and the trash can deletes it after a confirmation. A trip without items explains the list and offers **Recommend items** and **Add your own item**.
- **Recommendations.** **Recommend items** works out what to pack from what the trip already holds, only when selected, and opens it for review before anything is added. Each recommendation shows its category, its quantity and why it is recommended, such as "Lows around 37 °F in Vienna" or "For Untersberg hike in Salzburg", and every one starts checked. **Add chosen items** adds those still checked, not packed; **Cancel** adds nothing. A recommendation whose name is already on the list, whatever its capitals and spaces, isn't offered again: the review lists it as left as it is. So recommending again after the itinerary changes adds only what is new, and never changes or removes a saved item, its quantity or whether it is packed. Recommendations are never made, changed or added automatically.
- **Assumptions.** When the trip leaves something out, the review lists what was assumed instead, above the recommendations: a stay without nights makes quantities assume a week; a stay without dates can't use its monthly averages; typical weather may be for another time of year; a destination without weather gets a light layer instead of weather-specific clothing; no saved activities means no activity gear; and no saved entry requirements means a photo ID instead of a passport.

Recommendations follow fixed rules in `recommendPacking` (`src/lib/packing.ts`), from the trip's saved details alone: Travel looks nothing up, uses no live forecasts and asks no assistant. Each item is recommended once for the whole trip, however many destinations, activities or rules call for it, with the largest quantity any calls for and every reason.

- **Quantities.** Personal items, such as toothbrushes and passports, are one for each traveler, and shared ones, such as a first-aid kit, one for the party. Underwear, socks and tops are one a day, and pants or skirts one every 3 days, for each traveler, for the trip's days: its nights, once every stay has them, plus 1. Clothing covers a week at most, assuming laundry on longer trips, and a trip with a stay without nights, or without destinations, is assumed to take a week.
- **Weather.** Each stay's weather comes from its destination's monthly averages for the months of its dates, or else from its typical weather, and the warmest high, coldest low and wettest month of all the stays decide the clothing: from 70 °F, sunglasses and sunscreen; from 80 °F, shorts and a sun hat; below 60 °F, a light jacket or sweater; below 45 °F, a warm coat; below 32 °F, thermal base layers, a warm hat, warm gloves and a scarf; and from 2 inches of precipitation a month, a rain jacket or umbrella.
- **Activities.** Saved activities call for gear by terms in their names and what they are, matched as whole words in any capitalization, as transportation's are: terms such as hike or trekking call for hiking boots, a daypack, a reusable water bottle and insect repellent; such as swimming, beach, pool, snorkeling, surfing or hot springs for a swimsuit, flip-flops or water shoes and sunscreen; such as skiing, snowboarding or snowshoeing for ski goggles, waterproof gloves, thermal base layers and sunscreen; and fine dining, Michelin, opera, ballet, symphony, philharmonic, gala or black tie, in activities or restaurants, for a dressy outfit and dress shoes. The terms are `ACTIVITY_GEAR` in `src/lib/packing.ts`. A church saved for a destination whose Church shows, for a stay with a Sunday or without dates, calls for an outfit for Mass.
- **Travel and documents.** A connection whose transportation names an airplane calls for headphones, and one that names a car for a driver's license. Entry requirements saved for any destination call for passports and a power adapter; without any, a photo ID.
- **Essentials.** Every trip gets sleepwear, comfortable walking shoes, toiletries, a phone charger, a portable battery, booking confirmations, credit cards and some cash, prescription medications for its days plus extra, a first-aid kit and hand sanitizer.

Packing lists belong to their trip: deleting the trip deletes its list, and removing a destination from it keeps it. They are in the same backups. ChatGPT and Claude read each trip's list and can propose adding, changing, packing and deleting its items (see [AI assistants](#ai-assistants)). Schema 48 adds them, and every trip starts without any (see [deployment](docs/DEPLOYMENT.md#schema-48-packing-lists-tra-18)). Not included: separate lists for each traveler, shopping or prices, baggage allowances or weights, live forecasts, reminders, templates or copying lists between trips, offline use, and tracking which bag holds what.

## City suggestions
The Departing city, optional Return city, and City or destination fields use the [Open-Meteo geocoding API](https://open-meteo.com/en/docs/geocoding-api), with location data from [GeoNames](https://www.geonames.org/). Suggestions are optional; manually entered cities still work. They open when you type in the field or press the Down or Up arrow, not when it gets focus, so an editor that opens on a saved city shows no list and one Escape closes it (TRA-116). Searches of at least two characters are sent through `/api/locations`; adding a state or country (for example `Wooster, OH`) narrows results.

The suggestions float over the editor, so its scrolling fields never cut them off (TRA-140). They open below the field, or above it when the list at its full height doesn't fit below and there is more room above, and they never run past the part of the window you can see, which an on-screen keyboard shortens. They are as tall as before at most, about four suggestions; with less room they are shorter and their list scrolls. The Down and Up arrows scroll only that list, Enter chooses the highlighted suggestion, and Escape closes the list before the editor. Scrolling the editor's fields closes the suggestions, as a select's list closes, and typing or the arrows open them again. `dropdownPosition` in `src/lib/dropdown-position.ts` decides where they go.

Add destination also lists the trip owner's saved destinations first, marked **In your library**, in place of the suggestions that are them, even while suggestions load or when they are unavailable (TRA-142; see [Destinations](#destinations)). The arrows reach them first, and screen readers hear how many of the suggestions are in your library.

Departing city and Return city also suggest an airport when you type its three-letter IATA code, in any letter case (TRA-132). It comes first in the list, marked with an airplane, with its name and code, the city it serves and its country: `cle` suggests Cleveland Hopkins International Airport (CLE). Choosing it saves the code, `CLE`, which the [trip map](#trip-map) shows at the airport. City or destination suggests no airports, since a destination is a city. ICAO codes, such as `KCLE`, city codes, such as `NYC`, and unknown codes suggest no airport. Airports come from [OurAirports](https://ourairports.com/data/)' public-domain data: every airport with an IATA code, with its name, the city it serves, its country and its position, kept with the app in `src/lib/airports.json` and found by `src/lib/airports.ts`. Run `node scripts/update-airports.mjs` to refresh the list from OurAirports, and review its diff before committing it. Finding an airport needs no lookup, so airports count against none of Open-Meteo's limits.

A destination whose city was chosen from a suggestion displays as city and country, or city and state for US locations. The suggestion's full label is saved, keeping its region to distinguish same-named cities, and the destination records that it was chosen from a suggestion (TRA-76). Every other city displays exactly as entered, on cards, travel connections, page titles and in the editor, such as `Tokyo, Kyoto, Japan` or `Chicago, Cook County, IL`: text typed in, and a city ChatGPT or Claude proposes. Destinations saved before schema 26 recorded no suggestions, so schema 27 records once each whose city has a suggestion's shape (city, region and a country's full name), typed or not: `Vienna, State of Vienna, Austria` displays as `Vienna, Austria`, and `Tokyo, Kyoto, Japan` typed before then as `Tokyo, Japan`, while `Chicago, Cook County, IL` displays as entered (TRA-129; see [deployment](docs/DEPLOYMENT.md#schema-27-older-cities-chosen-from-suggestions-tra-129)). Choosing the same city from a suggestion again in the destination editor shows it shorter and keeps its travel connections; adding a city you already have to a trip keeps its destination as it is. The destination editor opens on the full saved city, so saving other changes, or the city unchanged, keeps the city and its connections; edited text is saved exactly as typed. Departing and return cities always display as saved.

The provider needs no key for this personal, non-commercial app. Its [free-service terms](https://open-meteo.com/en/terms) currently allow fewer than 10,000 calls per day, 5,000 per hour, and 600 per minute; commercial use needs a suitable plan or another provider. Lookup uses a four-second timeout, shares simultaneous matching queries, and keeps up to 200 queries in memory for ten minutes. The provider and response mapping live in `src/lib/location-search.ts`; Travel stores no coordinates or other location details, only whether each destination's city was chosen from a suggestion. The [trip map](#trip-map) looks saved places up through the same provider, within the same limits, as the [destination map](#destination-map) does its destination and the [map of all destinations](#map-of-all-destinations) every destination.

## Trip map
Each trip's page has a **The map** section below its header, before its destinations (TRA-44). It is open each time the page opens; its heading closes and reopens it, and reopening frames the map again. It shows the departing city, each destination in route order and the return city, with each connection's layovers and stops in their saved order. A trip that returns to its departing city has one marker for both. Destinations are numbered as on their cards, the departure, return, layovers and stops each have their own symbol, and a key below the map names the ones it shows.

Straight lines join each connection's places in travel order; they are not routes. Each connection shows the icons of its saved Transportation text, as in **Between the places**, a third of the way along its longest line from where it leaves, so a way out and back along the same line show apart. Lines take the shorter way across the 180th meridian.

An arrow on each line shows the way its connection goes (TRA-176), pointing from where the line leaves toward where it arrives, five sixths of the way along it, so the map reads from the departure through each destination, layover and stop to the return. A way out and back along the same line show their arrows at opposite ends, each near the place it arrives at, apart from each other and from both connections' transportation. Arrows are the same dark green arrowhead for every transportation, the same size at every zoom on desktops and phones, and stay on their lines as the map zooms, pans and resizes. Each line has one arrow, so a close view of part of a long line may show neither its arrow nor its transportation. Arrows sit below places and transportation, so they never cover them: where they meet, as when places are close together at a low zoom, the arrow is hidden beneath. Nothing selects or focuses an arrow, so clicks, taps and the keyboard reach places and transportation as before, and screen readers still hear each connection's route from its transportation. A line between places found at the same position has no arrow, and a place the map can't find has no line, so no arrow either. Arrows follow saved changes to the trip's destinations, their order and its connections, and change nothing saved.

When it opens, and whenever its places change, the map zooms and centers to show every place it found; otherwise it keeps your zoom and position. Drag to pan, and zoom with its + and − buttons, a double-click, or pinching. Once the map is selected, the keyboard pans and zooms it and the mouse wheel zooms it; before, the wheel scrolls the page. Selecting a place's marker with a pointer, a finger, Enter or Space goes to what it stands for and focuses it, without a popup: a destination's card, a layover's or stop's itinerary entry, and the departure or return to the connection leaving or reaching it. Selecting a connection's transportation opens its [popup](#transportation-popups) instead. A place's tooltip also names the place the map found for it.

Pointing to a destination's numbered marker with a mouse or pen, or reaching it with the keyboard, shows a preview of the destination beside the marker (TRA-143): its name as saved, below its primary photo, which fills the same 2:1 frame for every destination without stretching, cropped around the focal point saved for it. A destination without photos shows its name alone, with no empty frame. The preview goes above the marker, or below it where there isn't room above, and moves across as far as keeps it within the map, so a marker near any edge shows all of it; the map's zoom buttons and credits stay above it. It stays while the pointer is on the marker or the preview, closes a moment after the pointer leaves both or when the keyboard moves on, and Escape closes it. While the map moves, as when it brings a marker the keyboard reaches into view, the preview waits, then shows beside the marker. Touch screens have no hover, so a tap goes to the destination as before, without a preview, and selecting a place's marker still goes to what it stands for. The departure, return, layovers and stops show no preview, and transportation shows its popup instead. Screen readers hear the destination's name in its marker's label, so the preview, which repeats it, is hidden from them. The preview loads the photo's thumbnail from the versioned address the destination's gallery uses, served only to accounts that can open the destination, and changes nothing saved.

The map has no search or instructions of its own: the airport search that was above it is removed (TRA-144), as is the paragraph of instructions below its heading (TRA-145), so the map follows its heading directly, on desktop and phones. Departing city and Return city still [suggest airports](#city-suggestions), and the map still shows airport codes saved in a trip at their airports, as below.

The map never guesses where a place is. It looks each saved place up with Open-Meteo by the text before its first comma, leaving out anything in parentheses, such as an airport code, and uses the first place Open-Meteo has whose name is that text, or begins with it as whole words (`Frankfurt (FRA)` finds Frankfurt am Main), within every region or country written after it: a state or other region, a country or its code, a US state abbreviation, `USA` or `UK`. Letter case and accents don't matter, and a city chosen from the suggestions is found as chosen. A departure, return or layover written as an airport's three-letter IATA code in capitals, such as `PHL`, or chosen from the suggestions, is shown at that airport instead, without Open-Meteo (TRA-132). Codes must be in capitals, and destinations and other stops are always looked up by name, because names such as `Goa`, `Ulm` and `UAE` are also airport codes. A name with a code in parentheses, such as `Frankfurt (FRA)`, is still looked up by its name. **Not on the map**, below the map, lists the places it can't show, and why: none is saved, no place has that name, or the lookup couldn't be made right now, with **Try again**. A connection's lines join only its own places the map shows, so no line stands in for a missing place. Saved changes to destinations, connections, transportation and itinerary stops, including adding, removing and reordering them, update the map.

The page asks `/api/trip-map/<trip ID>` for the trip's places, which answers only accounts that can open the trip. Its lookups count against the city suggestions' limits on Open-Meteo calls, without a browser's own limits, run three at a time, and keep each name's places in memory for a day; after one fails, the rest wait for **Try again**. Airport codes need no lookup. Travel still stores no coordinates. [Leaflet](https://leafletjs.com/) draws the map, loaded only in the browser, and the browser loads its tiles from [OpenStreetMap](https://www.openstreetmap.org/copyright)'s tile servers, credited on the map. The trip, destination and itinerary data, prices, schedules and budgets are unchanged. Hotels, restaurants, activities and churches within a destination are on its own [destination map](#destination-map) (TRA-130).

### Transportation popups
Each connection's transportation on the map opens a popup of the connection (TRA-175). It shows the transportation's icons and the route, from where the connection leaves to where it arrives, named as its card in **Between the places** names them, then each of its saved details, only once saved: **Transportation** as typed, a flight's **Airline** and **Flight number**, which show only while its transportation names an airplane, as on its card, **Departure** and **Arrival** as saved, and **Time in transit**. Nothing unsaved shows as an empty field or a placeholder, so a connection with nothing saved shows its route alone. **View details** goes to the connection's card and focuses it, as selecting its transportation did before, and closes the popup.

Time in transit shows only when Departure and Arrival are both saved as a date and time with its offset from UTC, as ISO 8601 writes them, such as `2026-12-01T18:00-05:00` and `2026-12-02T08:30+01:00` (8 h 30 min), and the connection arrives after it leaves. A space may replace the `T`, seconds are optional, and `Z` means UTC. Without its offset, a time such as `Dec 1, 6:00 PM` could be in any time zone, so Travel never assumes one, nor a date for a time without one, and shows no time in transit rather than a guess. Departure and Arrival are still saved as typed, and their fields are unchanged.

Pointing to the transportation with a mouse or pen opens its popup. It stays while the pointer is on the transportation or the popup, so the pointer can move to View details, and closes a moment after the pointer leaves both. A click, a tap, Enter or Space opens it instead of going to the connection's card, and moves focus to View details without scrolling the page; it stays open until a click or tap elsewhere on the map, including on another marker, Escape, which returns focus to the transportation, or opening another connection's popup. Dragging the map, its zoom buttons and its credits leave it open, and while the map moves it waits, then shows beside the transportation. Touch screens have no hover, so a tap opens it. One connection's popup shows at a time; destinations' previews are unchanged.

The popup goes above the transportation, or below it where there isn't room above, and moves across as far as keeps it within the map, as a destination's preview does. Where it has room neither above nor below, it goes beside the transportation instead, on its right or else its left, so it never covers the transportation, where a click meant for it could select View details; only with room on no side, as on a phone's shorter map with the transportation near its middle, does it go as close to the transportation as the map allows. It covers the map's zoom buttons and credits while it shows, so nothing hides View details, and scrolls within the map when it is taller than the map has room for. Screen readers hear that the transportation opens a dialog and whether it is open, the route as the popup's name and its details as its description, and View details with the connection's route. The transportation has no tooltip, since its popup shows more. The popup reads the trip's saved connections, as their cards do, so it follows saved changes once the trip's data is read again, and it changes nothing: connections are edited in **Between the places**, and nothing is looked up for them.

## Destination map
Each destination card on a trip's page, and each destination's page in Destinations, has a **Map** section after the destination's photos and before its budget, ideas and research (TRA-130). On a trip's card it follows the card's name, stay notes and notes, which come after the photos. It is open each time the page opens, and its heading closes and reopens it. It shows every hotel, activity, restaurant and church saved for the destination, chosen for the budget or not, and the card and the destination's page show the same map from the same saved places. Each category has its own symbol, a bed, binoculars, a knife and fork or a church on its own color, and places found at the same spot, such as a hotel and its restaurant, share one marker showing how many there are.

The **Hotels**, **Activities**, **Restaurants** and **Churches** checkboxes above the map, each with its symbol, are all checked when the page opens. Any combination chooses the categories both the map and **Not on the map** show. Choosing saves nothing, looks nothing up, and isn't remembered.

When it opens, and whenever its markers move, the map zooms and centers to show every marker; otherwise it keeps your zoom and position. Drag to pan, and zoom with its + and − buttons, a double-click, or pinching. Once the map is selected, the keyboard pans and zooms it and the mouse wheel zooms it; before, the wheel scrolls the page. Selecting a marker with a pointer, a finger, Enter or Space opens a popup with each place there: its primary photo when it has one, its name and category, and **View details**, which takes focus; Escape closes the popup and returns focus to the marker. View details opens a hotel's, activity's or restaurant's details, as its card in [Hotels, Activities and Restaurants](#hotels-activities-and-restaurants) does, or a church's details, read only: its address, coordinates, denomination, website, Mass times and photos. A marker's tooltip also names the place the map found for it, or says it is shown at its saved coordinates. A place shown at approximate coordinates (TRA-150) has a dashed ring around its symbol, and its popup, tooltip and name for screen readers say it is an approximate location; a group's ring shows when every place in it is approximate. While one shows, a line below the map says what the ring means. None of them names an address, so an approximate place is never taken for a verified one.

A place's photo in its popup is its main photo, the one its card and details open on, at the top of its entry, above its name, category and View details (TRA-152). Every photo fills the same 2:1 frame, 240 pixels wide, or 180 on phones, without stretching: it is cropped to fit around its center, since hotel, activity, restaurant and church photos have no focal point, and the place's name and category wrap to its width. A place without photos shows its name, category and View details as before, with no empty frame or placeholder. Screen readers hear the place's name and category, which follow the photo, so the photo is hidden from them. A popup taller than the map has room for, as when places sharing a marker each have a photo, scrolls within the map rather than running past its edges, and the keyboard scrolls it to each View details in turn. A popup loads its photos' thumbnails only when it opens, from the versioned addresses the places' galleries use, served only to accounts that can open the destination, and changes nothing saved. Choosing a new main photo for a place, or removing its photos, changes its popup without looking the place up again, and a trip's destination card and the destination's page show the same photos.

Pointing to a marker with a mouse or pen, or reaching it with the keyboard, shows a preview of its places beside it, as the [trip map](#trip-map) previews a destination (TRA-188): for each place there, the photo its popup shows, when it has one, then its name and category, such as **Hotel**. A place without photos shows its name and category alone, with no empty frame, and places sharing a marker each show, in the popup's order. Like the trip map's, the preview is 200 pixels wide, or 160 on phones, and every photo fills the same 2:1 frame, cropped to fit around its center. It goes above the marker, or below it where there isn't room above, and moves across as far as keeps it within the map. Where it has room for neither, as when places sharing a marker each have a photo, it goes beside the marker, to its right or else its left, as a connection's popup on the trip map does, so it never covers the marker a click is meant for; one taller than the map has room for fills the map's height and scrolls. The map's zoom buttons and credits stay above it. It stays while the pointer is on the marker or the preview, closes a moment after the pointer leaves both or when the keyboard moves on, and Escape closes it without opening the popup. While the map moves, as when it brings a marker the keyboard reaches into view, the preview waits, then shows beside the marker. Selecting a marker still opens its popup, which closes the preview, and no preview shows while a popup is open, since it would cover the popup, nor for the marker focus returns to as a popup closes. Touch screens have no hover, so a tap opens the popup as before, without a preview. The preview shows only the places the checkboxes select, and closes whenever the map's markers change, as when a checkbox is checked or unchecked or a place is found, until the pointer or the keyboard reaches a marker again. Screen readers hear each marker's places in its label, so the preview, which repeats them, is hidden from them, and the keyboard never stops on it. It names no address, and an approximate place's preview shows its name and category as any other's, with its marker's dashed ring beside it. It changes nothing saved.

The map never guesses where a place is. It looks places up with [Nominatim](https://nominatim.org/), OpenStreetMap's search, within 50 km of the destination, which it finds as the [trip map](#trip-map) does. A place with an address is looked up by its address, which must lead to a building, house or other specific place: a street, square, neighborhood or town is too vague. A place without an address, or whose address leads to nothing specific, is looked up by its name, which must be one of the place's own names in OpenStreetMap, in any letter case and without accents, and never a street's, station's or stop's. A place shows only when exactly one place matches; matches within 100 m of each other, such as a hotel and its building, are one place. A place with [coordinates](#place-coordinates) saved in its editor is looked up by its address alone, never its name, and shows where its address is found; when it isn't, or the place has no address, it shows at its coordinates instead, however far from the destination, as Melk Abbey does on Vienna's map (TRA-163). **Not on the map**, below the map, lists the selected categories' places it can't show, by category, each with why and **View details**: no place nearby has its address or name, more than one place nearby matches, or the lookup couldn't be made right now, with **Try again**. A place whose coordinates wait for review since its address changed is looked up by its new address, and listed, saying so, when it isn't found. When the map can't find the destination itself, it says so, places with coordinates show at them, and the rest are listed. When no place in the selected categories can be shown, a message replaces the map. Adding or deleting a place, or saving a new name, address or coordinates for it or a new city for the destination, updates the map, each place on one marker at most; other changes, such as a price or a budget selection, look nothing up again.

The page asks `/api/destination-map/<destination ID>` for its places, which answers only accounts that can open the destination, and sends Nominatim only the saved addresses and names it looks up: never the name of a place with coordinates to show, nor anything of one with coordinates and no address. [Nominatim's usage policy](https://operations.osmfoundation.org/policies/nominatim/) for its public server allows Travel at most one request a second, made one at a time, asks that Travel name itself (`TravelPlanner/1.0`), keep answers rather than ask again, and credit OpenStreetMap's data, and forbids heavy use, systematic or bulk queries, and autocomplete. So Travel's requests wait their turn, more than a second apart, each answer is kept in memory for a day, and the credit is below the map. After a request fails, the places waiting behind it are unavailable until **Try again**, and after Nominatim says there have been too many requests, or refuses one, lookups pause for a minute. The server waits up to eight seconds for a map's places, and the map asks again for any still waiting their turn, so a destination with many new places fills in over a minute or more, and at once after that. Travel stores no coordinates it finds, only those people save or approve. Should Nominatim's operators ask Travel to stop, or its use outgrow the policy, another provider can replace it in `src/lib/place-search.ts`.

## Map of all destinations
The **Destinations** page has a **Map** section below **Saved destinations**' heading and search, above the destination cards (TRA-180). It is open each time the page opens; its heading closes and reopens it, which keeps the search, and reopening frames the map again. It shows each destination the cards can show, by its saved ID: your own and those a trip shared with you visits, in a trip or not, each once however many trips visit it. Each destination found has a pin on the trip map's destination green. Hotels, activities, restaurants and churches are on each destination's own [map](#destination-map), and journeys on each [trip's map](#trip-map).

When it opens, and whenever the positions of the destinations it shows change, as when the search changes, the map zooms and centers to show every one, at most as close as a trip's map frames one place; otherwise it keeps your zoom and position. Drag to pan, and zoom with its + and − buttons, a double-click, or pinching. Once the map is selected, the keyboard pans and zooms it and the mouse wheel zooms it; before, the wheel scrolls the page. Selecting a destination's pin with a pointer, a finger, Enter or Space opens the destination's page, and its tooltip names the place the map found for it.

Destinations whose pins would cover each other at the map's zoom share one marker instead, showing how many there are, so a pin never hides another: zoomed out to the whole world, a country's cities may share one, which zooming in sets apart, and two destinations found at the same place, such as `Vienna` and `Vienna, Austria`, share one however far in the map zooms. Selecting a shared marker with a pointer, a finger, Enter or Space opens a popup with a link to each of its destinations' pages, and moves focus to the first; Escape closes it and returns focus to the marker. Its tooltip names its destinations.

Each destination is named as its card names it, by its full saved city when another destination's card would show the same short name, such as `San Jose, Nueva Ecija, Philippines` and `San Jose, Occidental Mindoro, Philippines`, so screen readers tell same-named cities apart by the region or country saved with them. A destination shared with you that has the same name as another, as when a trip shared with you visits its owner's `Vienna` and you saved your own, also says whose it is: `Vienna, shared by` its owner. A shared marker's name for screen readers lists every destination on it.

The page's search filters the map and **Not on the map** with the cards, and clearing it shows every destination again. The map never guesses where a destination is: it looks each up by its saved city with Open-Meteo, as the [trip map](#trip-map) looks up a trip's destinations, and shows it only at the place found. **Not on the map**, below the map, lists the destinations the search shows that the map can't, each linking to its page, and why: no place was found by that name, or the lookup couldn't be made right now, with **Try again**. A destination found once stays on the map while a later lookup of the same city can't be made. When no destination is saved, none matches the search, or none of those shown can be found, a message replaces the map. Adding, renaming or deleting a destination, and trips being shared with you or no longer, update the map once the page shows the change, and a renamed destination is never shown where its old city was; other changes, searching, zooming and closing the map look nothing up again.

The page asks `/api/destinations-map` where each destination is, which answers only with the destinations the signed-in account can open, by their IDs, each with the city it was looked up by and the place found for it, and nothing else of them. Its lookups count against the city suggestions' limits on Open-Meteo calls, run three at a time and keep each name's places in memory for a day, as the trip map's do. Viewing and using the map change nothing saved, and Travel stores no coordinates. [Leaflet](https://leafletjs.com/) draws the map, loaded only in the browser, with [OpenStreetMap](https://www.openstreetmap.org/copyright)'s tiles, credited on the map. It is 380 pixels tall, or 300 on phones, and never makes the page scroll sideways.

## Place coordinates
A hotel, activity, restaurant or church can have coordinates, so its [destination map](#destination-map) shows it where they are when its address can't be found, matches more than one place, or is withheld, as a vacation rental's often is (TRA-150).

- **Entering.** **Coordinates (optional)**, below the address in the editor of each hotel, activity, restaurant and church, has **Latitude**, from −90 to 90, negative south of the equator, and **Longitude**, from −180 to 180, negative west of Greenwich, in degrees with any number of decimal places, as map apps show them. Either needs the other, and **Accuracy** needs a choice: **Exact** when they mark the place itself, or **Approximate** when they mark only roughly where it is. Travel checks the range only, never whether they are right. Clearing both and saving removes them.
- **On the map.** The address comes first (TRA-163). Unless its coordinates wait for review, a place with an address is looked up by it alone, never by its name, and shows where exactly one place within 50 km has it, as a place without coordinates does. When none or more than one does, or the lookup can't be made, the place shows at its coordinates instead, however far from the destination, and never under **Not on the map**. A place without an address shows at them at once, without asking Nominatim. While its address is looked up, it is on neither the map nor the list. Approximate ones are marked as approximate, never as an address. What a lookup finds never changes saved coordinates or addresses. Changing coordinates looks nothing up again; adding or removing them looks the place up again.
- **Address changes.** Saved coordinates belong to the address they were saved with. Once a save changes the place's address, by anyone, from any page or an assistant, the coordinates wait for review: the map doesn't use them and looks the place up by its new address instead, and its details say so. Its editor then shows them with **These coordinates are right for this address**. Saving with that checked, or with new coordinates, confirms them for the address; clearing them removes them. The editor shows the same choice as soon as the address field changes, so they can be confirmed in the same save.
- **Details.** A place's details show its coordinates below its address, latitude first, with their accuracy, or **Not added**.
- **Sharing.** Coordinates belong to the place, so every trip that visits the destination uses the same ones, and everyone who can open the destination can change them. Changing them never changes a place's address, what it is, photos, price, budget selection, notes, links or list order. ChatGPT and Claude can propose them, one place or many at once (see [AI assistants](#ai-assistants)).
- **Upgrade.** Schema 38 starts every existing place without coordinates, so every map looks as it did until some are saved (see [deployment](docs/DEPLOYMENT.md#schema-38-place-coordinates-tra-150)).

## Routes, itineraries, and research links
Trips return to their departing city by default. Select **Return to a different city** to enter a separate endpoint. Existing trips retain their departure location and default return behavior.
Each travel connection supports up to 30 ordered layovers or stops, with a place, arrival/departure details, and notes. A flight's layovers show with its airline and flight number, and its other stops under **Stops along the way** (see [Flights and their layovers](#flights-and-their-layovers)). The connection's estimated price covers the whole itinerary and is counted once in the trip budget, as is its optional [miscellaneous spending](#miscellaneous-spending-in-transit). The price is typed, with cents if needed, such as 12.50; its field has no increment and decrement arrows (TRA-49).
Each connection in **Between the places** shows an icon for each kind of transportation its saved Transportation text names, once per kind and in the order entered: airplane (flight, airplane, flying, air, jet, plane, fly), train (train, rail, subway, tram, railway), car (car, driving, rental car, taxi, rideshare, road, Uber, Lyft, drive, ride share), bus (bus, coach, shuttle), boat (boat, ferry, cruise, ship, sea, water), walking (walking, on foot, walk), and bicycle (bike, bicycle, cycling). The terms for a vehicle or a ride also match their plurals: flights, airplanes, planes, jets, trains, subways, trams, cars, rental cars, taxis, rideshares, ride shares, Ubers, Lyfts, buses, coaches, shuttles, boats, ferries, cruises, ships, bikes, and bicycles. Terms match as complete words or phrases in any capitalization, so "Train and flight" shows a train and then an airplane, "Flights and ferries" an airplane and then a boat, and "Airbnb" matches nothing. Blank or unrecognized text shows a generic route icon. The Transportation field stays free text, and saved connections show the icons for what they say without being changed; the terms live in `src/lib/transportation-methods.ts`.
Connections and hotel/activity/restaurant ideas support up to 20 research links with optional short descriptions. Existing single links are retained during the additive database upgrade. Older schema versions upgrade to the current version automatically inside a transaction; take an online backup before deploying this upgrade.

## Airline and flight number
A connection by air can keep its airline and flight number, entered by hand, so each flight in a trip is easy to identify (TRA-147).

- **Entering.** In **Plan this connection**, **Airline** and **Flight number** appear below **Transportation** while its text names an airplane, as the connection's airplane icon shows: Flight, Plane or another airplane term, alone or with other kinds, as in "Train and flight" (see [Routes, itineraries, and research links](#routes-itineraries-and-research-links)). They appear and hide as you type. Each is one optional line of up to 120 characters, saved as typed, such as Delta and DL 123. Travel doesn't look them up or check them against any airline. A connection has one of each, layovers included; a layover's notes can name its other flights.
- **Where they show.** On the connection's card in **Between the places**, below its transportation and times, as **Airline** and **Flight number**, each only once entered, with the flight's layovers directly below them (see [Flights and their layovers](#flights-and-their-layovers)), and in its transportation's [popup on the trip map](#transportation-popups) (TRA-175). A connection without them shows neither label.
- **Other transportation.** While the Transportation text names no airplane, the editor hides both fields and the card and the map's popup show neither, but they stay saved, and saving keeps them: naming a flight again shows them in the editor, on the card and in the popup. Nothing else about other kinds of transportation changes.
- **Saving.** **Save changes** saves them with the connection's other details, and **Cancel** discards them. Clearing a field and saving removes it. Each connection keeps its own, so flights in the same trip can have different airlines. They never change the connection's price, times, notes, links, itinerary, layover plans or any budget. **Clear** clears them with the rest of the travel plan, as does a route or city change that clears the connection. A save from a page opened before them, which doesn't send them, keeps them.
- **Sharing.** They belong to the trip, so everyone who can open it sees and changes them, and no one else. ChatGPT and Claude read them with the trip's travel and can propose them with a connection's other details, and the proposal's page shows them as **Airline** and **Flight number**.
- **Upgrade.** Schema 41 starts every existing connection without them, so no trip looks different until they're entered (see [deployment](docs/DEPLOYMENT.md#schema-41-airline-and-flight-number-tra-147)).

## Miles required
A flight can keep how many airline miles it would cost, beside its cash price, so the two ways of paying for it can be compared (TRA-186).

- **Entering.** In **Plan this connection**, **Estimated miles required** appears directly below **Estimated price (USD)** while the Transportation text names an airplane, as for the [airline and flight number](#airline-and-flight-number), appearing and hiding as you type. It is the total for the whole party for the full connection, layovers included, as the price is; travelers never multiply it. It takes a whole number from 0, such as 85000, and blank means unknown, never 0. A negative, fractional or invalid number is refused, changing nothing. Its field has no increment and decrement arrows, as the price's has none. Travel never looks miles up, checks award availability or works them out: they are only what you enter.
- **The price stays the price.** **Estimated price (USD)** stays the cash price, entered, checked and budgeted as before, so a flight can have a price, miles, both or neither. Miles are never money: Travel never converts them to dollars, values them or estimates savings, and they never change **Travel**, the trip estimate or whether it is complete, so a flight with miles but no price still shows **Needs estimate**.
- **Where they show.** On the connection's card in **Between the places**, directly below its price, as a whole number with thousands separators, such as *85,000 miles required*, only once entered. **Clear** shows for a connection with only them.
- **Other transportation.** While the Transportation text names no airplane, the editor hides the field and the card doesn't show them, but they stay saved: the hidden field is left out of the save, which keeps them, so nothing typed in it before the change can stop the save. Naming a flight again shows them in the editor and on the card.
- **Saving.** **Save changes** saves them with the connection's other details, and **Cancel** discards them. Clearing the field and saving removes them. They never change the connection's airline, flight number, price, times, nights spent traveling, notes, links, itinerary or layover plans. **Clear** clears them with the rest of the travel plan, as does a route or city change that clears the connection. A save from a page opened before them, which doesn't send them, keeps them.
- **Sharing.** They belong to the trip, so everyone who can open it sees and changes them, and no one else. ChatGPT and Claude read them with the trip's travel and can propose them with a connection's other details, and the proposal's page shows them as **Estimated miles required**.
- **Upgrade.** Schema 53 starts every existing connection without them, so no trip looks different and no estimate changes (see [deployment](docs/DEPLOYMENT.md#schema-53-miles-required-tra-186)).

## Flights and their layovers
A flight's layovers are part of the flight, so a journey with connecting flights reads, and is edited, in one place (TRA-184). A connection is a flight while its Transportation text names an airplane, as for its [airline and flight number](#airline-and-flight-number).

- **In the editor.** In **Plan this connection**, **Layovers** comes below **Airline** and **Flight number**, before the price: each layover with its **Stop type**, **Place**, **Arrival at stop**, **Departure from stop** and **Stop notes**, the arrows that reorder it and the trash can that removes it, then **Add layover**. The flight's other stops and points of interest stay under **Stops along the way**, at the end, with **Add stop**. Typing in Transportation moves the layovers between the two as soon as it names, or stops naming, an airplane.
- **On the trip page.** A flight's card in **Between the places** shows its layovers directly below its airline and flight number, in their saved order, each with its [plan](#layover-plans) or **Plan layover**, then the connection's notes and links, then its other stops. Each layover and stop shows once.
- **One itinerary.** Layovers and other stops are still one ordered itinerary, saved as before. The arrows move an entry among its own list only, so the other list's entries keep their places in travel order, and **Add layover** and **Add stop** add an entry last. Changing an entry's **Stop type** moves it to the other list, keeping its place in travel order; a layover with a plan still says that saving it as another kind of stop removes the plan. The limit of 30 counts layovers and stops together, so the editor shows no count beside either heading, and each list says so once the connection has 30.
- **Other transportation.** While Transportation names no airplane, **Stops along the way** lists every layover and stop in travel order, with **Add layover** and **Add stop**, as before apart from its count, so layovers saved for a flight stay there to edit or remove. Naming a flight again shows them with it.
- **What stays the same.** Nothing saved changes: layovers keep their IDs, order, notes, times and plans, the trip map's markers lead to them as before, and prices, miscellaneous spending and budgets are unchanged.

## Layover plans
Each layover in a connection's itinerary can have a plan for the time between its two flights (TRA-45). In **Between the places**, **Plan layover** under a saved layover opens **Layover in** and its place; a layover added in **Plan this connection** has it once the connection is saved. Travel suggests no activities and supplies no estimates: you enter everything, and the plan shows only what follows from what you enter.

- **Flights.** **Airport time zone** lists the time zones the browser knows, by region, each named by its place with its offset from UTC on the arrival's date, such as Berlin (UTC+2). **Arriving flight lands** and **Connecting flight departs** are each a date and time as the airport's clocks show them, from your booking, and the connecting flight must depart after the arriving flight lands. The layover's length counts the time zone's daylight saving changes and any change of date: a layover in London from 10:00 PM to 6:00 AM on the night the clocks go back is 9 hours, and one overnight or across a month or year is counted to the minute. A time the clocks skip is refused, and a time they repeat is read as the first. The layover's own Arrive and Depart, in Plan this connection, stay free text, and the plan never reads them.
- **Airport time.** **Immigration**, **Customs**, **Security**, **Terminal transfer** and **Boarding**, how long before departure to be at the gate, are each your own estimate in whole minutes from 0 to 1440. A new plan starts each at 0: leave 0 for any that doesn't apply.
- **Activities.** Up to 20, in order, each with **What**, an optional **Where**, whether it is **In the airport** or **Outside the airport**, its **Duration** in whole minutes from 1 to 1440, and optional **Notes**. One outside the airport also has **Travel there**, from the airport or the activity before it, from 0 to 1440 minutes. The arrows reorder activities and the trash can removes one. Activities outside the airport go one after another, in a single trip out of the airport, with **Travel back to the airport** after the last of them.
- **Schedule.** Worked out again as you type, from landing to departure in order of time: immigration and customs, the airport activities listed before those outside it, each activity outside the airport after its travel there, the travel back, security and the terminal transfer, the other airport activities, any time to spare, and being at the gate for boarding. A step of 0 minutes is left out. Each step shows its time on the airport's clocks, with the date where it changes, and how long it takes. Above the steps, the plan says how much time it leaves before boarding, or before departure without a boarding estimate.
- **Warnings.** A plan that needs more time than the layover leaves is **Over by** the difference: it says the plan reaches the gate after boarding time and could miss the connecting flight, or that it ends after the connecting flight departs, and by how much. Steps that end after boarding time are orange and marked **Late**, and the gate and the departure keep their scheduled times among them.
- **Estimates.** Only the two flights' times are marked **Scheduled**. Every other time is an estimate from what you entered, and every schedule says it isn't a guarantee.
- **On the trip page.** A saved plan shows under its layover: the layover's length, airport time, travel and activities, and the time to spare or the warning, with **Schedule** opening its steps. **Edit plan** opens its editor, and **Remove plan**, once confirmed, removes the plan and nothing else.
- **What changes it.** A plan has no prices, and saving or removing it changes no trip, destination, budget or other travel detail. It goes with its layover: removing the layover from its connection, changing it to another kind of stop, clearing the connection, or a route or city change that clears or removes the connection removes its plan. **Plan this connection** says so beside a layover that has one.
- **Sharing.** Plans belong to the trip, so everyone who can open it sees and changes them, and no one else. ChatGPT and Claude read them with the trip's travel and can propose them with `leg.layoverPlan`, for the owner to approve (see [AI assistants](#ai-assistants)).
- **Upgrade.** Schema 39 adds the plans' table, with every layover starting without one (see [deployment](docs/DEPLOYMENT.md#schema-39-layover-plans-tra-45)).
## Images
Each destination, hotel, activity, restaurant, and church can have up to 10 photos, with one selected as the main photo on its card. Each trip can have one [headline image](#trip-headline-images) as well. Click the thumbnails to view the other photos. Add photos, choose the main photo, or remove individual photos in the editor; removing the main photo selects another remaining photo. Cancel discards photo changes. Existing single idea images become the main photo automatically.

Hotel, activity and restaurant photos show at one size within each list, whatever their shape (TRA-124, TRA-137). In a destination's Hotels, Activities, Restaurants and Churches carousels, every card's photo fills the same 4:3 frame, in all four and at every screen width, and on each category's page each idea's main photo fills the same 16:7 frame. Photos are cropped to fit around their center, never stretched, and the frames keep their size while photos load and as you choose other photos. A carousel card without photos shows its category's icon in a frame of the same size. On the Activities page, an activity without photos shows the activity icon in an empty frame of the same size, and a hotel or restaurant without photos shows none on its page. Saved photos, their order and the main photo are unchanged, as are destination photos and church galleries.

With a mouse or trackpad, drag a photo in any photo editor onto another photo to put it in that photo's place (TRA-126). The editor's instructions mention it, and the pointer shows a grab hand over each photo. The photo being dragged is outlined, and a bar on one side of the photo under the pointer shows whether it will go before or after it. Photos show in their new order as soon as you let go, new photos not yet saved included, and the order is saved with the destination, hotel, activity, restaurant or church. Cancel discards it, and **Undo photo changes** restores the saved order. Dragging keeps the main or primary photo and changes no photo or other detail. Every gallery shows its photos in their saved order. Phones and tablets don't drag photos, and their editors are unchanged. Hotel, activity, restaurant and church photos are arranged only by dragging.

Destination galleries also have **Move left** and **Move right** controls in the editor to save photo order. The primary photo opens first, independently of its position in the thumbnail order. Removing it chooses the first remaining photo. Schema 17 preserves each existing destination image, including its bytes and version, as that destination's primary photo. Existing single-image URLs continue to serve the current primary photo; individual photo URLs retain ownership and version checks. Ordinary destination edits preserve the gallery.

Destination galleries with two or more photos also have left and right arrows on the edges of the main photo, which show the previous and next photo in the saved order (TRA-123). The right arrow on the last photo shows the first, and the left arrow on the first photo shows the last. With a mouse, the arrows appear while the pointer is over the main photo or either arrow has keyboard focus; on touchscreens they always show. The counter, the selected thumbnail and the **Primary photo** label follow the photo shown, and the thumbnails still choose any photo. Browsing saves nothing: the order and primary photo stay as saved, and the gallery opens on the primary photo again each time the page loads. A destination with one photo has no arrows, and hotel, activity and restaurant galleries have none.

Church galleries browse the same way (TRA-136). A church with two or more photos has the same left and right arrows on the edges of its main photo, on its card on its Church page and in its details, opened from its card in **Churches** or from the [destination map](#destination-map), and they show the previous and next photo in the saved order, looping as a destination's do. On a touchscreen, swiping the main photo to the left shows the next photo and swiping it to the right shows the previous one, looping the same way. A swipe is a move of at least 40 pixels, more sideways than up or down, with one finger or a pen: moving up or down on the photo still scrolls the page, pinching still zooms it, and a mouse doesn't swipe. The counter, the selected thumbnail and the **Main photo** label follow the photo shown, the thumbnails still choose any photo, and each church's gallery browses on its own. Every photo fills the same 16:7 frame, cropped to fit and never stretched, and stays centered, since church photos have no focal point. Browsing saves nothing and never leaves the church: its photos, their order, its main photo and its other details stay as saved, and its gallery opens on the main photo again each time the page loads. A church with one photo shows it without arrows, thumbnails or swiping, and a church without photos shows no gallery, as before. Destination galleries don't swipe.

Each destination photo has its own focal point, which decides what its crop shows (TRA-53). The main photo's 16:7 frame crops every photo to fit, and a photo starts centered, as every saved photo and every new upload does. In the destination's photo editor, **Adjust crop** under a photo opens the crop editor in place of the photos: the photo in a 16:7 frame, the main photo's shape on every screen. Drag the photo with a mouse or a finger to choose what shows, and the frame shows the new crop as you drag. A photo moves only the way it is wider or taller than the frame, and only as far as its edges: most photos move up and down, and a panorama wider than 16:7 moves sideways. Zoom isn't offered. **Reset to center** centers the photo again, **Apply** keeps the new crop as an unsaved change and returns to the photos, and **Cancel** returns to them keeping the crop applied before. Saving the destination saves every applied crop, and canceling the destination's editor or **Undo photo changes** discards them. The main photo and the gallery's thumbnails keep each photo's focal point in view, on desktop and on phones, whichever photo is shown or primary, and so do the editor's photos and the primary photo on the destination's card in Destinations (TRA-131). Adjusting a crop changes nothing else: the photo file, the photo order and the primary photo stay as they were, and dragging in the crop editor never moves a photo to another place. Hotel, activity, restaurant and church photos have no focal point. Schema 30 starts every saved destination photo centered (see [deployment](docs/DEPLOYMENT.md#schema-30-destination-photo-focal-points-tra-53)).

On phones, up to 540 pixels wide, a trip's destination cards show the main photo edge to edge across the top of the card, inside its border, instead of inside the card's padding, so it is 32 pixels wider and taller to match: 352 × 154 pixels instead of 320 × 140 on a phone 390 pixels wide (TRA-155). It keeps the main photo's 16:7 shape, so it shows the crop chosen in the crop editor, around each photo's focal point and without stretching, and its arrows, counter, **Primary photo** label and thumbnails work as before. Destination pages, and tablets, desktops and phones turned sideways wider than 540 pixels, keep the photo inside the card's padding. With a mouse at those phone widths, each **+** between the cards (TRA-153) takes a row as tall as itself, 32 pixels instead of 17, so it still never covers a photo.

Uploads may be JPEG images, `.jfif` and `.jpe` files included, or PNG, WebP, AVIF, GIF, TIFF, BMP or HEIC images, `.heic` and `.heif` files, up to 5 MiB each and 20 megapixels, with at most 15 MiB of new files in one save (TRA-179). Travel decides what a file is from what it holds, never from its name or the type the browser gives it. A photo editor takes a file whose type or extension is one of these, since browsers give some, such as `.jfif` and `.heic` files, an unexpected type or none, and saving refuses a file holding anything else, such as an SVG image, whatever it is called. Only still images are taken: an animated GIF, WebP, PNG or AVIF, a TIFF of more than one page, or a HEIC file holding more than one image or a sequence is refused, and a GIF of one frame is a still image. An image of more than 20 megapixels is refused before it is decoded, and a damaged one, or one saved in a way Travel can't read, such as a bitmap holding a JPEG, is refused as unreadable; each refusal says why. Images are oriented, a phone's HEIC photo turned as it was taken included, resized to fit 1600 × 1200, converted to sRGB, a HEIC photo's Display P3 colors included, stripped of metadata, and saved as WebP (up to 2 MiB each), and an upload larger than that also keeps a [large version](#large-photo-versions) for wide frames on high-resolution screens. All selected uploads must be valid before any changes are saved, and a refused save changes no saved photo.

A photo editor shows each new photo as the browser shows it, and when the browser can't, as for a HEIC photo, or a TIFF image, outside Safari, it shows Travel's preview instead: the photo saving would keep, as WebP (TRA-179). The preview is made for a signed-in account from Travel's own pages, checked as saving checks the file, and kept by neither Travel nor the browser. A file Travel can't read either shows no preview, and saving it says why. Sharp decodes JPEG, PNG, WebP, AVIF, GIF and TIFF images; HEIC images, whose HEVC-coded pixels sharp can't decode, are decoded by libheif's WebAssembly build (`libheif-js`), and bitmaps by Travel itself, then converted as every upload is.

Every photo editor, for destinations, hotels, activities, restaurants and churches, also has **Add image by URL** beside **Add photos**, and the trip editor has it beside **Add image** for a trip's headline image (TRA-139). It opens a field for the web address of an image itself, not of the page it's on. **Preview**, or Enter in the field, has Travel download the image and shows it whole. **Use this image** then adds it as if you had chosen it from your device: it shows with the other new photos, to arrange, crop, choose as the main or primary photo, or remove, it counts toward the same limits, and saving uploads and prepares it as every upload is. Travel keeps its own copy, so the photo stays when its source changes or goes away. **Cancel** closes the field without adding anything, and changing the address forgets the image shown. Travel downloads only from `http://` and `https://` addresses of public internet hosts, never private, loopback or link-local ones, checked for the address given, each of up to 3 redirects, and every address a host name resolves to as Travel connects. The image must be of one of the formats uploads take, as its server says (it may call a bitmap `image/x-ms-bmp`, as nginx does), of up to 5 MiB, that downloads within 15 seconds, and it is checked as an upload is before it shows, so an image you preview is one saving accepts. Otherwise the field says why, such as an address that isn't an image or a server that answered 404, and nothing is added. Only signed-in accounts can download images this way, from Travel's own pages.

Each photo is saved with a thumbnail, which the galleries' thumbnails and the photo editors' previews show instead of the photo (TRA-89), as do the trip map's destination previews and the destination map's previews and popups. A thumbnail is the whole photo as WebP, scaled down only as far as it still covers 480 × 320, so it fills those frames without being enlarged and a destination photo's thumbnail keeps its focal point in view. For a card with 10 typical photos, that is under 0.5 MB of thumbnails instead of about 3.7 MB of photos. The main photo, the crop editor, the idea carousels' cards, the destination cards in Destinations and the proposal page's photos still show the photo itself. A trip's headline image has no thumbnail, since it shows only in its card and banner, at their size. Thumbnails are served under each photo's address with `/thumbnail` added, versioned and only to accounts that can see the photo, as photos are. A photo saved before schema 32 has no saved thumbnail, so one is made from the photo whenever a browser asks for it, and browsers keep it as they keep photos (see [deployment](docs/DEPLOYMENT.md#schema-32-photo-thumbnails-tra-89)).

Images live in the same persistent SQLite database and are included in online backups. Snapshots carry only photo IDs, versions, widths, destination photos' focal points, trips' headline image crops, and the main selection; image routes serve separate, versioned responses. Image-only edits preserve travel plans, prices, research links, and budget selections.
ChatGPT and Claude can propose photo changes and trips' headline images, downloaded and prepared by the same rules, for the designated owner to approve (see [AI assistants](#ai-assistants)).

### Large photo versions
From feedback that the Japan trip's headline image looked soft (TRA-154): a photo is saved at most 1600 × 1200, but a trip's banner is up to 1,248 pixels wide, which a high-resolution screen draws with 2,496 pixels, and more once its crop is zoomed in. So an upload larger than the photo also keeps a large version beside it: the whole photo as WebP, oriented and without metadata like the photo, scaled down only as far as it fits 2560 × 1920 and never enlarged. Destination, hotel, activity, restaurant and church photos keep one, as do trips' headline images and the photos ChatGPT and Claude propose, whether chosen from a device or added by URL.

- **Which loads.** Every frame that shows the photo itself, the trip's banner and card, the destination's main photo and its card in Destinations, the idea and church galleries, the idea and church carousels' cards and the crop editors, offers both, and the browser loads the large version only when the frame, zoomed as a headline image's crop is, shows more pixels than the photo has. On high-resolution laptops and desktops that includes the trip banner and a destination's main photo; ordinary screens, tablets and phones load the photo, unless a headline image's crop is zoomed in far enough. Thumbnails, the trip map's previews and the proposal page's photos are unchanged.
- **Limits.** Each large version is up to 5 MiB, enough for the hardest images to compress at that size; uploads keep their limits. Preparing an upload takes longer: about 0.8 seconds instead of 0.3 for a 12-megapixel photo in testing.
- **Saved photos.** Travel keeps no original upload, so a photo or headline image saved before schema 40, or one no larger than 1600 × 1200, has no large version and shows exactly as before. Choosing a larger original again, as a new upload, gives it one. Nothing is enlarged or sharpened artificially, and crops, focal points, order and main photos are unchanged.
- **Serving.** Large versions are served under each photo's or headline image's address with `/large` added, versioned and only to accounts that can see the photo, as photos are. Snapshots give each photo's width and its large version's, or none, so pages can offer them (see [deployment](docs/DEPLOYMENT.md#schema-40-large-photo-versions-tra-154)).

## Saving after a deploy
Every deploy builds with the same Server Actions key, so a page opened before a deploy keeps saving after it. If a save reaches a version of the planner that doesn't recognize it, because the key or the save action itself changed, it shows **The planner was updated. Your changes haven't been saved. Please reload the page and try again.** instead of the connection error, since trying again without reloading never works. Adding an item from a page opened before TRA-75, which doesn't send the new item's ID, shows the same message; that page's changes to saved items keep working. So does saving monthly averages from a page opened before TRA-158, which doesn't name each month; clearing them still works. Deploying requires the key; see [deployment](docs/DEPLOYMENT.md#server-actions-key-tra-74).

## Database failures
A save the database can't complete, as when the disk is full, saves nothing and shows **We couldn't save your changes. Please try again.** The server log names SQLite's own error, such as `database or disk is full`, rather than an error from undoing the save (TRA-93). Saving works again once there is room, without a restart.

If the database can't be opened, because its file isn't a database or another process holds its write lock, the request that tried fails and closes its connection, and the next request tries again. While another process holds the write lock, each try waits up to 5 seconds for it. The Docker image also opens the database before its server starts, so there a database that can't be opened or upgraded stops the container instead (see [Hosting](#hosting)).

## Hosting
The existing GitHub Actions deployment builds a Node container and deploys it to Dokku at travel.dev.boyersoftware.com after checks pass. Only `main` deploys, only to the server with the verified SSH host key, and with the 20 MiB request limit photo uploads need; see [deployment safeguards](docs/DEPLOYMENT.md#deployment-safeguards-tra-98).
The container opens and upgrades the database before its server starts, and Dokku switches traffic to a new release only once its `/api/health` returns HTTP 200. A release that can't open or upgrade the database, such as one older than the database's schema, stops instead, so its deploy fails and the running release keeps serving (TRA-78); see [startup and health checks](docs/DEPLOYMENT.md#startup-and-health-checks-tra-78).

## Backups
```sh
pnpm backup ./backups/travel-2026-10-07.sqlite
```
The backup uses SQLite's online backup API, checks integrity, and refuses to overwrite an existing backup.
It writes a temporary snapshot beside the new backup, so that disk needs free space for about twice the database.
A backup that fails, as on a full disk, reports SQLite's error, such as `database or disk is full`, and leaves no temporary files.
It reads `TRAVEL_DATABASE_PATH` from the environment, then `.env.local`, then `.env`, and otherwise backs up `data/travel.sqlite`.
Store backups outside the repository and keep a copy off the server.
